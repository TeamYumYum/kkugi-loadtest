# kkugi-loadtest

꾸기의 사용자 행동을 재현하고 서비스의 안정성과 처리 성능을 검증하는 Locust 기반 인공 트래픽 발생기입니다.

계정마다 페르소나와 개인 특성을 배정하고, 식사 기록·음식 검색·요약 조회 등의 행동을 수행하도록 설계합니다. 일상적인 사용 패턴을 재현하는 상시 시뮬레이션과, 사용량을 높여 병목을 확인하는 부하 테스트를 함께 지원하는 것이 목표입니다.

> 현재는 프로젝트 초기화 단계입니다. 아래 내용은 구현 방향이며, 실행 가능한 시나리오와 배포 설정은 아직 제공하지 않습니다.

## 목표

- 사용자별 페르소나, 인증 정보, 이전 행동과 개인 상태를 유지합니다.
- 식사 시간대와 사용자별 이용 빈도에 따라 자연스러운 트래픽을 발생시킵니다.
- API 응답뿐 아니라 식사 저장 등 실제 업무 결과를 검증합니다.
- 장시간 실행으로 안정성을 확인하고, 단계적으로 부하를 높여 성능 병목을 찾습니다.
- 동일한 시나리오와 데이터 조건에서 개선 전후의 성능을 비교합니다.

## 사용자와 부하 모델

`n`은 시뮬레이션 대상이 되는 **전체 고유 계정 수**입니다. 초기 규모는 `n=1,000`으로 계획합니다.

| 항목 | 의미 |
| --- | --- |
| 전체 계정 수 `n` | 페르소나와 개인 상태를 유지하는 고유 계정 수입니다. |
| DAU | 하루 동안 실제로 서비스를 이용한 고유 계정 수입니다. |
| 동시 활동 사용자 수 | 같은 시점에 업무 세션을 수행하는 사용자 수입니다. |
| 업무 세션 | 앱을 열고 점심 식사를 기록하는 등 한 번의 서비스 이용 흐름입니다. |
| RPS | 초당 HTTP 요청 수입니다. |
| 업무 처리량 | 식사 기록 성공 건수나 완료 세션 수 등으로 측정합니다. |

전체 계정 수와 Locust에서 실행 중인 User 수, 동시 활동 사용자 수는 구분합니다. 대기 중인 User가 존재할 수 있으며, 업무 세션은 로그인 세션이나 TCP 연결과도 다릅니다.

상시 시뮬레이션의 RPS는 페르소나 구성, 활동 빈도, 시간대, 세션별 요청 수와 응답 시간에 따라 달라집니다. 개별 요청의 시작 시각을 고정하기보다 사용자 행동을 모델링합니다. 구체적인 활동 비율과 빈도는 서비스의 페르소나 정의를 확인해 결정합니다.

### 계정별 정보

- **페르소나:** 시나리오 선택과 행동 경향을 정의합니다.
- **개인 프로필:** 목표 칼로리, 선호 음식, 평소 식사 시간, 접속 빈도 등을 유지합니다.
- **실행 상태:** 토큰, 기록한 식사, 응답에서 얻은 ID, 다음 활동 시점 등을 관리합니다.

## 분산 실행 구조

```text
상시 실행 서버
 ├─ Master 프로세스 1개
 └─ Worker 프로세스 1개 ──┐
                         │
팀원 노트북               ├─ 각 Worker가 대상 앱 서버로 직접 요청
 └─ 추가 Worker들 ────────┘

모든 Worker → 같은 Master에 연결하여 통계와 상태 보고
```

Master는 실행을 제어하고 통계를 집계합니다. 실제 가상 사용자와 HTTP 요청은 Worker에서 실행합니다. 팀원 노트북의 Worker는 계획한 피크 부하 실험에 활용합니다.

- Worker 추가는 트래픽 생성 자원을 늘리는 작업입니다. 실제 부하를 높이려면 활동 사용자 수나 세션 발생량도 함께 조절해야 합니다.
- 계정을 Worker에 중복 배정하지 않도록 관리합니다. Worker 재시작이나 이탈 시 계정 상태가 자동 이전된다고 가정하지 않습니다.
- 상시용 계정과 추가 부하용 계정을 구분하는 방안을 검토합니다. 구체적인 배정 및 복구 정책은 구현 시 정합니다.
- 성능 측정 시 발생기를 대상 앱 서버와 분리하는 것을 원칙으로 합니다. 관측 서버에 함께 배치한다면 지표 수집에 영향을 주지 않도록 자원 여유를 확인합니다.

## 첫 번째 시나리오: 다이어터의 점심 기록

아침 식사를 이미 기록한 사용자가 음식 두 개를 검색해 점심을 저장하고, 변경된 요약을 확인하는 흐름입니다.

| 순서 | API | 목적 |
| --- | --- | --- |
| 1 | `GET /daily-summaries/{date}` | 오늘 요약 조회 |
| 2 | `GET /daily-goals/{date}` | 오늘 목표 칼로리 조회 |
| 3 | `GET /growth/me` | 연속 달성 기록 조회 |
| 4 | `GET /meals?date=...` | 기존 끼니 목록 조회 |
| 5 | `GET /foods?keyword=...` | 첫 번째 음식 검색 |
| 6 | `GET /foods?keyword=...` | 두 번째 음식 검색 |
| 7 | `POST /meals` | 검색 결과의 음식 ID로 점심 저장 |
| 8 | `GET /daily-summaries/{date}` | 저장 후 요약 재조회 |

위 경로는 초기 설계 기준입니다. 실제 API prefix와 요청·응답 필드는 서비스의 API 명세에 맞춰 구현합니다.

검색 결과에서 실제 음식 ID를 사용하고, 계정과 날짜에 맞는 저장 결과를 검증합니다. 초기 데이터 준비, 검색 결과가 없는 경우, 중복 기록, 재시도와 재실행 정책도 함께 다룹니다. 자동 API 호출과 사용자가 검색·선택하는 단계의 대기 시간을 구분합니다.

사진 시나리오는 S3 이전과 관련 기능 준비가 끝난 뒤 추가합니다.

## 관측과 검증

다음 지표를 함께 수집할 계획입니다.

- 전체 및 API별 요청 수, RPS, 응답 시간 p50/p95/p99, 실패 원인
- 예정·시작·완료·실패·누락 세션 수와 시작 지연
- 실제 DAU, 동시 활동 사용자 수, Worker별 실행 상태
- 앱 서버·DB·발생기의 CPU, 메모리, DB 연결과 쿼리 지연
- 네트워크 송수신량과 장시간 실행 중 자원 사용 추이

Worker가 Master로 보고한 요청 통계를 서버 내부의 Prometheus·Grafana와 연결하는 방안을 검토합니다. 구체적인 수집 연동은 아직 구현하지 않았습니다.

처음에는 소수 계정으로 기능과 상태 격리를 검증하고, `n=1,000` 규모로 하루 또는 이틀 실행합니다. 안정성과 실제 활동량을 확인한 뒤 계정 수를 늘립니다. 응답 시간과 오류율의 합격 기준은 초기 측정과 서비스 요구에 맞춰 명시합니다.

장시간 실행의 성공과 최대 처리량은 별도로 평가합니다. 처리 성능은 같은 시나리오·데이터·서버 조건에서 응답 시간과 오류율 기준을 만족하는 처리량으로 비교합니다.

## 구현 순서

1. 서비스의 페르소나 정의, API 명세, 인공 계정 인증 방식을 확인합니다.
2. 계정 한 명의 점심 기록 세션을 구현하고 업무 결과를 검증합니다.
3. 소수 계정으로 상태 격리, 중복 방지, 재시도와 통계를 확인합니다.
4. 페르소나별 프로필과 일일 활동 스케줄을 추가합니다.
5. Master·Worker 실행 구성과 계정 배정 정책을 구현합니다.
6. 지표 수집을 연결하고 상시 시뮬레이션을 시작합니다.
7. 추가 Worker를 활용한 점진적 부하 실험을 진행합니다.

## 실행 안내

실행 명령, 환경 변수, 의존성 설치 방법과 배포 절차는 첫 시나리오 구현과 함께 추가합니다. 인증 토큰과 비밀값은 저장소에 포함하지 않습니다.
