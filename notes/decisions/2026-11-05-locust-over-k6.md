# 상시 트래픽은 Locust로, 한계 측정은 k6로

| 항목 | 값 |
|---|---|
| 날짜 | 2026-11-05 (결정은 2026-10-28, 발생기 설계 논의 때) |
| 상태 | 결정 |
| 관련 | [트래픽 모양과 규모](2026-10-29-traffic-shape.md) 근거 4항, [시작 규모와 관측 서버 부담](2026-10-29-start-scale-and-load.md), 서비스 저장소 `docs/operations/synthetic-traffic.md`(이하 운영 문서) |

## 배경

도구는 설계 논의(2026-10-28) 때 정했지만 결정 기록이 없었다. 당시 인계 문서에 남은 이유는 "사용자별 페르소나, 개인 특성, 이전 행동과
계정 상태를 유지하기 쉽다"는 한 줄뿐이다. 이 기록은 그 선택을 지금의 구현에 비추어 다시 적은 것이다.

설명할 때 "k6로는 안 된다"고 말하지 않는다. 사실과 다르다. k6도 VU(가상 사용자)마다 상태를 들고 반복할 수 있고, 확장(xk6)을 직접
빌드하면 외부 저장소도 쓸 수 있다. 이 기록의 논지는 **"우리 요구사항을 채우는 비용이 Locust에서 더 낮았다"**이다.

## 결정

- **상시 인공 트래픽(운영 문서의 A)은 Locust로 만든다.** 이 저장소의 발생기다.
- **처리량 한계와 순간 몰림(운영 문서의 B)은 k6 부하 테스트로 잰다.** 발생기는 한계 측정을 맡지 않는다.

## 근거

### 목적

발생기는 서버를 한계까지 미는 부하 테스트 도구가 아니다. 인공 계정 수만 개가 며칠, 몇 주 동안 현실적인 하루를 보내며 운영 서버에
데이터를 쌓는 상시 트래픽이다. 아래 비교는 이 목적을 전제로 한다.

### 목적에서 나오는 요구사항

- 계정마다 페르소나, 개인 특성, 이전 행동이 이어진다. 발생기는 계정별 하루 일정을 만들고(`kkugi_load/scheduler.py`), 시각이 된
  세션을 실행한다.
- 발생기를 다시 띄워도 계정 상태가 남는다. 토큰, 회원 ID, 온보딩 여부, `generation`을 SQLite(`state/accounts.db`,
  `kkugi_load/accounts/state.py`)에 저장한다.
- 며칠씩 끊지 않고 돌리면서 중간에 규모를 바꾼다. 배율, 정지, 설정 다시 읽기, 거버너가 이 일을 한다(`kkugi_load/control.py`,
  `kkugi_load/governor.py`).
- 프로세스 여러 개가 계정을 나눠 맡는다. 지금은 관측 서버의 상시 Worker 8개가 풀을 하나씩 맡고, 설계 당시에는 중요한 시간대에 팀원
  노트북의 Worker를 붙였다 떼는 운영도 합의했다. Master는 Worker의 계정 범위가 겹치지 않는지 확인한다(`kkugi_load/distributed.py`).
- 필요한 부하가 작다. 2,000명 기준선의 1분 최대가 2.83 TPS([저녁 기준선](2026-11-04-baseline-2000-evening.md))이고, 목표인
  20,000명의 피크 추정치도 28~56 RPS다([트래픽 모양과 규모](2026-10-29-traffic-shape.md) 결과 절).

### 구현 방식: Locust User는 계정이 아니다

"Locust는 User 객체가 사용자 한 명의 상태를 들고 있어서 쉽다"는 설명은 이 저장소의 구현과 맞지 않는다. 발생기에서 Locust User는
계정이 아니라 실행기다(`locustfile.py` 첫 주석, [용어집](../../docs/glossary.md)). 계정 상태는 Worker 프로세스의 Python 객체와 SQLite에
있고, 실행기는 일정표에서 세션을 하나씩 꺼내 실행한다.

그래서 Locust가 실제로 덜어 준 것은 사용자 모델이 아니라 아래 세 가지다.

- **시나리오가 평범한 Python 코드다.** 일정 계산, 확률 분포, `sqlite3`를 표준 라이브러리 그대로 쓴다.
- **Master/Worker 분산 실행과 그 사이의 사용자 정의 메시지가 기본 기능이다.** 계정 범위 확인과 배율 전달은 `register_message`·
  `send_message` 위에 얹었다. Worker가 끊길 때 실행기를 다시 나누는 동작도 `--enable-rebalancing` 옵션 하나로 켠다.
- **웹 UI와 통계에 직접 끼어들 수 있다.** 조절 경로(`/kkugi/*`)를 Master 웹 UI에 더했고, `SESSION`·`SCHEDULE`·`ACCOUNT` 같은
  사용자 정의 통계를 Locust 통계에 함께 보낸다.

### 요구사항별 구현 비용

| 요구사항 | Locust | k6 |
|---|---|---|
| 계정별 일정과 영속 상태 | Python 코드와 `sqlite3`로 바로 구현함 | VU마다 상태를 들 수는 있다. 그러나 시나리오 안에서 파일이나 DB에 쓰는 기능이 기본에 없어, 확장을 빌드하거나 저장 서버를 따로 둬야 함 |
| 여러 프로세스가 계정을 나눠 맡음, Worker 합류와 이탈 | Master/Worker와 메시지가 기본 기능임 | 오픈소스판에는 분산 실행 기능이 없음. k6-operator(쿠버네티스)나 Grafana Cloud가 필요함 |
| 무기한 상시 운영 중 조절 | 실행 시간을 정하지 않고 띄우고, 웹 UI에 조절 경로를 더함 | 실행 기간과 단계(stage)를 정한 테스트가 기본 형태임. `externally-controlled` 실행기로 어디까지 대신할 수 있는지는 확인 필요 |
| 높은 부하를 내는 효율 | 불리함. Python 프로세스 하나가 코어 하나만 씀 | 유리함(Go 기반). 다만 위의 부하 규모에서는 필요하지 않음 |

k6로도 만들 수는 있다. 하지만 추가로 만들어야 할 것이 많고, k6의 강점인 발생 효율은 이 용도에서 쓰이지 않는다.

### 포기한 것과 보완

Locust는 닫힌 모델(closed model: 응답을 받아야 다음 요청을 보내는 방식)로 돈다. 서버가 느려지면 요청도 덜 보내므로 지연이 실제보다
작게 측정된다. 그래서 처리량 한계는 발생기로 재지 않고, 요청 속도를 고정할 수 있는 열린 모델(open model, k6의 `arrival-rate`
실행기)로 k6 테스트에서 잰다. 운영 서버가 유일한 환경이라 상시 트래픽을 한계까지 올리면 실사용자 응답과 CPU 크레딧이 깎인다는
이유도 있다([트래픽 모양과 규모](2026-10-29-traffic-shape.md) 근거 4항).

즉 어느 한쪽이 무조건 나은 것이 아니라 용도에 맞게 나눠 쓴다.

### 버린 선택지

| 선택지 | 버린 이유 |
|---|---|
| 상시 트래픽도 k6로 만듦 | 영속 상태, 분산 실행, 상시 조절을 확장이나 별도 장치로 직접 만들어야 한다 |
| 한계 측정도 Locust로 함 | 닫힌 모델이라 서버가 느려질 때 지연을 작게 잰다 |

## 한 문장 요약

목적이 부하 측정이 아니라 계정별 상태를 유지하며 장기간 데이터를 쌓는 것이었고, 그 요구에는 Python으로 쓰는 시나리오와 Master/Worker
구조가 추가 작업 없이 맞았다. 대신 Locust가 약한 한계 측정은 k6로 따로 한다.

## 기록의 출처

- 당시 기록에 명시된 이유는 상태를 유지하기 쉽다는 한 줄뿐이다. 나머지 근거는 당시 합의한 요구사항과 지금의 구현, 도구 특성을 맞춰
  본 해석이다. 대외적으로 설명할 때는 이 점을 감안한다.
- k6에 관한 서술은 공개 문서 기준의 일반 지식이고, 이 저장소에서 k6로 직접 확인하지 않았다.
