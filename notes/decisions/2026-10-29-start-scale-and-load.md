# 시작 규모와 관측 서버 부담

| 항목 | 값 |
|---|---|
| 날짜 | 2026-10-29 |
| 상태 | 결정 |
| 대체 | [트래픽 모양과 규모](2026-10-29-traffic-shape.md)의 "첫 운영일 10,000개"와 미결 "관측 서버 사양" |

## 배경

발생기의 서버 Worker는 관측 서버에서 돈다. 관측 서버는 사양이 높지 않고, 같은 서버에서 Prometheus·Loki·Tempo·Grafana가 backend의 관측 데이터를 받는다. 트래픽을 많이 보내면 수집이 흔들릴 수 있다.

## 결정

- **관측 서버는 Lightsail Medium 4GB다.** vCPU 2개, 메모리 4GB, SSD 80GB, CPU 기준선은 vCPU당 20%다(운영 문서 7.1절).
- **계정 1,000개로 실측한 뒤 올린다.** 이후 10,000 → 20,000은 실측값으로 계산해 버틸 수 있을 때만 올린다.
- 실측에서 잴 값: 요청 1건당 발생기 CPU, 요청 1건당 Loki·Tempo 증가량, 관측 서버의 CPU 크레딧 추이.
- 수집 쪽 작업(추적·로그 샘플링, 서버 CPU 수집)은 서비스 저장소에 맡긴다. 작업 지시서는 이 저장소에 두지 않는다.

## 근거

부담은 두 종류이고 줄이는 방법이 다르다.

| | 발생 부담 | 수집 부담 |
|---|---|---|
| 무엇 | 발생기가 요청을 만들고 보내는 CPU·메모리 | backend가 남긴 로그·추적·지표를 받아 저장하는 일 |
| 비례하는 것 | 서버 Worker가 보내는 요청 수 | backend가 받은 전체 요청 수. 누가 보냈는지와 관계없다 |
| 노트북 Worker로 옮기면 | 줄어든다 | 줄지 않는다 |
| 줄이는 방법 | 발생기 컨테이너의 CPU·메모리 상한, User 수 상한, 연결 재사용 | 추적·로그 샘플링(서비스 저장소 작업) |

## 결과

### 트래픽 양 (확정한 표 기준)

계정 하나가 하루에 앱을 여는 기대 횟수는 약 4회다(밤 0.05 + 일반 1.0 + 완충 1.5 + 피크 1.5). 세션당 평균 요청은 6건으로 가정했다.

| 항목 | 1,000개 | 10,000개 | 20,000개 | 참고: 운영 문서 가정 |
|---|---|---|---|---|
| 하루 세션 | 약 4천 | 약 4만 | 약 8만 | 약 5.8만 |
| 하루 요청 | 약 2.4만 | 약 24만 | 약 49만 | 약 58만 |
| 피크 RPS | 약 1 | 약 11 | 약 22 | 약 28 |

### 실행기(Locust User) 수 정정

앞 기록의 "피크 동시 세션 약 1,000개"는 운영 문서의 세션 길이 3분 가정으로 계산한 값이라 틀렸다. 우리 세션의 길이는 설정의 생각 시간으로 정해진다.

- 식사 기록 세션: 검색 대기 2~6초와 선택 대기 1~4초가 음식 두 개만큼 들어가 약 15초
- 조회 세션: 생각 시간이 없어 1초 안팎

계정 20,000개의 피크는 시간당 약 10,000세션, 1분 약 170, 초당 약 3, 동시 진행 약 42개다. 여유를 두면 서버 Worker에 User 약 100개, 노트북 Worker(1,000개)에 약 10개면 된다. 실제 세션 길이는 `SESSION` 통계로 확인해야 한다.

### User와 세션의 관계

- User 하나는 한 번에 세션 하나만 실행한다. 한 Worker의 동시 세션 상한은 그 Worker가 받은 User 수다.
- 세션 안의 대기(생각 시간, 응답 대기) 동안에는 같은 프로세스의 다른 User가 실행된다. Locust가 시작할 때 gevent `monkey.patch_all()`로 `time.sleep`과 네트워크 대기를 협력형으로 바꾸기 때문이다(Locust 2.47.0 코드에서 확인).
- 1분에 20,000세션 같은 순간 몰림은 User 수가 아니라 요청 속도(초당 약 2,700건)가 발생기와 backend의 한계를 넘어 불가능하다. 순간 몰림은 상시 트래픽이 아니라 k6 스파이크 테스트(B)에서 다룬다.
