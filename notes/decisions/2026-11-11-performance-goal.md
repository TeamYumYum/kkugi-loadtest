## 배경

8,000명 단계가 처음으로 하루(2026-11-10, 한국 시간 00:00-24:00)를 채웠다. 다음 날 하루 요약(`tools/daily_report.py`)에
API 8개의 p95가 300ms를 넘었다는 주의가 붙었다. 사용자는 "유의미하게 느린 게 맞다"고 판단하고 성능 개선을 시작하기로 했다.
개선은 목표 숫자를 먼저 정하고, k6로 부하를 주며 얼마나 견디는지 재는 방식으로 한다.

이 기록은 개선 전의 서버 상태, 개선이 필요한 이유, 최종 목표를 남긴다. 아래 숫자가 개선 전후를 비교할 "개선 전" 값이다.

## 성능 개선이 필요한 이유

1. **계정 수가 2배가 될 때마다 응답 시간은 2-6배로 늘었다.** 1분 최대 TPS는 4,000명(26.9)과 8,000명(24.6)이 비슷한데,
   같은 기간 `GET /growth/me` p95는 152 → 633ms, `GET /daily-goals/{goalDate}` p95는 53 → 347ms가 되었다. 순간 요청량이
   아니라 회원 수와 쌓인 데이터에 따라 느려지는 것으로 보인다(추정). 이 추세면 20,000명에서는 기준을 더 크게 넘는다.
2. **자원이 남는데도 느리다.** JVM CPU 평균 4.9%, 버스트 여유 97.9% 이상, 데이터 서버 CPU 평균 16%다. 요청이 적은 오전
   구간에서도 `GET /growth/me`는 p50부터 132ms다. 서버를 키워서 해결할 문제가 아니라 요청 하나의 비용(쿼리, 코드)을 줄여야 하는
   문제로 보인다(추정).
3. **커넥션 풀이 모자라기 시작했다.** 4,000명까지는 최대 3개만 썼는데, 8,000명에서 10개가 다 차고 23시대 몰아 기록 세션 구간에
   재시작 없이도 최대 27개가 기다렸다. 같은 시각 MySQL에서 실행 중인 스레드는 최대 4개였다. 커넥션을 잡은 채 DB 밖에서 시간을
   쓰는 코드가 있을 수 있다(추정, 확인 필요).
4. **실사용자가 같은 API를 쓴다.** 인공 요청이 아닌 요청 중 가장 많은 것이 `GET /growth/me`와 `GET /daily-summaries/{date}`다.
   둘 다 가장 느린 API에 속한다.

## 결정

### 진행 방식 (사용자 결정)

- **목표는 API 하나가 아니라 전 범위에 하나로 정한다.** API들이 커넥션 풀과 DB를 함께 쓰므로, 한 API만 고치면 병목이 다른
  API로 옮겨 갈 수 있다. 성격이 다른 API에 예외 기준을 둘 수는 있지만, 측정하기 전에 정해 둔다.
- **병목 순서로 하나씩 고친다.** 잴 때마다 목표를 가장 크게 깨는 원인 하나를 고치고, 같은 시나리오로 다시 잰다. 목표를 이미
  지키는 API는 손대지 않는다.
- **목표 부하에서 기준을 지키면 마친다.** 마지막 측정을 기준선으로 남기고, 이후의 회귀는 하루 요약의 p95 비교로 잡는다.
- 상시 트래픽(Locust)은 지금처럼 두고, 한계 측정은 k6의 열린 모델(`constant-arrival-rate` 등)로 한다.

### 목표 (제안값, 확정 전)

| 단계 | 조건 | 합격 기준 | 판정 근거 |
|---|---|---|---|
| 1. 지금 부하 | 8,000명 상시 트래픽, 하루 | 모든 API p95 300ms 이하, 커넥션 대기 0 (재시작 직후 5분 제외) | 하루 요약 (서버 기준) |
| 2. 목표 부하 | k6 혼합 요청 **60 RPS**를 30분 유지 | 모든 API **p95 300ms, p99 800ms 이하**, 오류율 0.1% 미만, 커넥션 대기 0 | k6 (클라이언트 기준), 원인 분석은 서버 기준 |
| 3. 여유 | k6 혼합 요청 **120 RPS**를 10분 유지 | 무너지지 않음: 오류율 1% 미만, p99 3,000ms 미만 | k6 (클라이언트 기준) |

- **최종 목표는 2단계와 3단계를 함께 통과하는 것이다.** 1단계는 k6 환경이 정해지기 전에도 확인할 수 있는 중간 목표다.
- k6 측정에서는 목표와 별도로 **한계**도 기록한다. 요청 속도를 계단식으로 올려 p95 300ms가 처음 깨지는 RPS다.
- 혼합 요청의 API별 비율은 11-10 인공 요청의 비율(위 API 표의 요청 수)을 그대로 쓴다.
- 판정에서는 처음 5분을 JVM 워밍업 구간으로 보고 뺀다.

## 근거

| 값 | 근거 |
|---|---|
| 60 RPS | 8,000명의 1분 최대 24.6 TPS × 2.5배(20,000명) ≈ 61. [트래픽 모양과 규모](2026-10-29-traffic-shape.md)의 20,000명 피크 추정 28-56 RPS와도 맞는다. 계정 수에 비례한다는 가정이다 |
| 120 RPS (2배) | 순간 몰림과 데이터 증가에 대한 여유. 가정이다 |
| p95 300ms | 하루 요약이 이미 쓰는 주의 기준(`MAX_API_P95_MS`)과 같게 해서 상시 트래픽과 k6 결과를 같은 잣대로 본다. 가정이다 |
| p99 800ms | 지금 p99가 1,000ms를 넘는 API가 있어 꼬리도 따로 묶는다. 가정이다 |
| p99 3,000ms (3단계) | 거버너가 배율을 낮추는 기준과 같다 |
| 오류율 0.1% | 지금 하루 실패가 0건이므로 엄격하게 둔다. 가정이다 |

버린 선택지:

| 선택지 | 버린 이유 |
|---|---|
| 느린 API마다 목표를 따로 정함 | 공유 자원 때문에 한 API의 개선이 다른 API를 느리게 할 수 있고, 이를 판정하지 못한다 |
| 평균 응답 시간으로 판정 | 지금 문제는 꼬리(p95, p99)에 있다. 평균은 이를 가린다 |
| 지금 부하(25 TPS)만 목표로 함 | 20,000명 단계를 버틸 수 있는지 답하지 못한다 |
| 서버 증설로 해결 | 자원 사용률이 낮아 효과가 작을 것으로 본다. 개선 뒤에도 목표에 못 미치면 다시 검토한다 |

## 미결

- **목표 숫자 확정.** 위 값은 제안값이다. 성격이 다른 API(예: `POST /workout-sessions`)에 예외 기준을 둘지도 함께 정한다.
- **k6를 쏠 환경.** 운영 서버가 유일한 환경이다. 운영 서버에 쏘면 실사용자 응답과 버스트 크레딧이 깎이고, 크레딧이 남아 있을 때
  잰 한계는 크레딧이 바닥난 뒤보다 높게 나온다. 선택지는 새벽(02-05시) 운영 서버, 운영 DB를 복사한 별도 환경, 쿼리 분석을
  먼저 하고 k6를 나중에 하는 순서다. 권장은 마지막이다. 부하 없이도 느린 API는 쿼리 로그와 실행 계획으로 먼저 볼 수 있다.
- **서비스 저장소 수정은 팀과 함께 한다.** 이 저장소는 k6 시나리오와 측정 기록을 맡는다.
- **16,000명 증량과의 순서.** 전후 비교는 같은 계정 수에서 해야 한다([상시 트래픽을 흘리는 이유](2026-11-09-why-continuous-traffic.md)
  근거 절). 개선 전에 증량할지 정해야 한다.
- **backend 재시작 20회의 원인.** 09:45-17:14에 몰려 있고, 그 시간대 앱 서버 CPU(1시간 최대)가 87-99%였다. 성능 목표와는 별개지만,
  재시작 직후마다 커넥션 대기와 CPU 100%가 생긴다(확인 필요).
- **데이터 서버의 버스트 크레딧.** `t3` 계열이지만 크레딧 설정과 잔량을 확인하지 않았다(확인 필요).
