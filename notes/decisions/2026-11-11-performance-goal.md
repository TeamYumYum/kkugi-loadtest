## 요약

- **무엇을**: 꾸기 backend의 응답 시간을 개선한다. 목표 숫자를 먼저 정하고, 고칠 때마다 같은 방법으로 다시 잰다.
- **왜**: 인공 계정 8,000명이 보내는 초당 7-8건 남짓의 요청에서 이미 홈 화면 API가 새벽(유휴)보다 크게 느려진다. 18시의 p50은
  `GET /growth/me`가 7배, `GET /daily-goals/{goalDate}`가 24배다. 이때 CPU,
  커넥션 풀, DB 어느 것도 다 쓰지 않았다. 서버를 키워서 풀리는 문제가 아니라 원인을 찾아 고쳐야 하는 문제로 본다. 계정을
  20,000명까지 늘릴 계획인데, 계정 수가 2배가 될 때마다 p95는 2-6배로 늘어 왔다.
- **목표**: 20,000명 피크에 해당하는 초당 60건의 혼합 요청에서 모든 API의 p95 300ms, p99 800ms 이하를 지키고, 그 2배(120건)에서도
  무너지지 않는다. 부하가 없을 때는 이미 모든 API가 이 기준 안에 든다. 즉 "부하가 걸려도 유휴 때에 가까운 성능을 유지한다"가 목표다.
- **아직 정하지 않은 것**: 목표 숫자 확정, k6를 쏠 환경, 16,000명 증량과의 순서.

## 배경

꾸기는 식단·운동 기록 앱이다. 이 저장소의 발생기는 인공 계정으로 운영 서버에 현실적인 하루를 흉내 낸 요청을 계속 보낸다. 부하
테스트로는 드러나지 않고 회원 수와 쌓인 데이터에서만 드러나는 문제를 실사용자보다 먼저 겪기 위해서다
([상시 트래픽을 흘리는 이유](2026-11-09-why-continuous-traffic.md)). 계정 수는 2,000 → 4,000 → 8,000 → 16,000 → 20,000으로
2배씩 늘리고, 단계마다 하루 이상 지켜본다.

8,000명 단계가 처음으로 하루(2026-11-10 화요일, 한국 시간 00:00-24:00)를 채웠다. 다음 날 하루 요약(`tools/daily_report.py`)에
API 8개의 p95가 300ms를 넘었다는 주의가 붙었다. 사용자는 "유의미하게 느린 게 맞다"고 판단하고 성능 개선을 시작하기로 했다.

이 기록은 개선이 필요한 이유, 개선 전의 서버 상태, 최종 목표를 남긴다. 아래 숫자가 개선 전후를 비교할 "개선 전" 값이다.

## 성능 개선이 필요한 이유

### 1. 초당 7-8건에서 이미 몇 배씩 느려진다

같은 날 같은 서버에서, 요청이 거의 없는 새벽과 요청이 몰리는 시간대를 비교했다. backend 재시작이 없던 시간대만 골랐다.
응답 시간은 서버 기준(ms)이다.

| 시 | TPS | `GET /growth/me` p50 / p95 | `GET /daily-goals/{goalDate}` p50 / p95 |
|---|---:|---:|---:|
| 03시 (유휴) | 0.08 | 52 / 115 | 6 / 12 |
| 07시 (아침 봉우리) | 6.53 | 207 / 452 | 101 / 310 |
| 18시 (저녁 봉우리) | 7.89 | 380 / 805 | 145 / 447 |
| 23시 (몰아 기록 세션) | 9.56 | 102 / 764 | 9 / 326 |

- `GET /growth/me`의 p50은 새벽 52ms에서 18시 380ms로 7배가 된다. `GET /daily-goals/{goalDate}`는 6ms에서 145ms로 24배다.
- 초당 7-8건은 서버 한 대에 큰 부하가 아니다. 이 정도에서 느려진다면, 요청이 더 늘었을 때는 더 나빠질 것으로 본다.

### 2. 그때 어떤 자원도 다 쓰지 않았다

| 시 | JVM CPU 평균 | 앱 서버 CPU 평균 | 커넥션 풀 최대 사용 | 커넥션을 얻는 데 걸린 평균 시간 | 데이터 서버 CPU 평균 | MySQL 행 잠금 대기 |
|---|---:|---:|---:|---:|---:|---:|
| 03시 | 0% | 2% | 0/10 | 0.6ms | 44% (주) | 0회 |
| 07시 | 2% | 5% | 3/10 | 26ms | 4% | 6회, 합계 27ms |
| 18시 | 11% | 19% | 5/10 | 4.7ms | 11% | 1회, 합계 9ms |
| 23시 | 14% | 25% | 10/10 | 1.5ms | 10% | 1회, 합계 125ms |

주: 03시에는 요청이 거의 없으므로 backend와 무관한 데이터 서버 작업으로 보인다(확인 필요).

- CPU와 DB에 여유가 있고, 커넥션 풀도 23시를 빼면 절반 이상 비어 있었다. 서버 사양을 올려도 효과가 작을 것으로 본다.
- 07시에는 커넥션 풀에 빈자리가 있는데도 커넥션을 얻는 데 평균 26ms가 걸렸다(새벽 0.6ms). 원인 후보 중 하나지만 아직 확인하지
  않았다. 다른 후보는 앱 서버와 데이터 서버 사이의 네트워크(서로 다른 클라우드다), 세션 시작이 같은 초에 몰리는 순간 부하다.
- 즉 **느려지는 원인을 아직 모른다.** 원인을 찾는 것이 개선 작업의 첫 단계다.

### 3. 계정이 늘 때마다 더 나빠지고 있다

| 지표 | 2,000명 저녁 | 4,000명 주말 | 8,000명 (11-10) |
|---|---:|---:|---:|
| 하루 평균 TPS | 0.49 | 1.39 | 2.64 |
| 18시 TPS (1시간 평균) | 1.78 | 3.64 | 7.89 |
| `GET /growth/me` p50 / p95 (하루) | 29.7 / 76.4 | 67.9 / 152.1 | 178.1 / 632.8 |
| `GET /daily-goals/{goalDate}` p95 (하루) | 17.2 | 53.1 | 347.3 |
| `POST /workout-sessions` p95 (하루) | 153.1 | 227.0 | 514.5 |
| 커넥션 풀 최대 사용 / 대기 | 3/10, 0 | 3/10, 0 | 10/10, 62 |

- 요청 수는 단계마다 약 2배가 되었는데, p95는 2-6배가 되었다. 요청 수보다 빠르게 나빠진다.
- 단, 이 비교에는 계정 수 말고도 달라진 것이 있다. 아래 "이 기록의 한계"에 적었다.

### 4. 앞으로 부하가 더 늘어난다

계정 수는 20,000명까지 늘릴 계획이다([트래픽 모양과 규모](2026-10-29-traffic-shape.md), 사용자 결정). 지금의 2.5배다. 3의 추세가
이어지면 20,000명 전에 응답 시간이 사용자가 기다림을 느끼는 수준(1초)을 넘는다(추정).

### 5. 사용자가 기다리는 화면이다

- 느린 API 셋(`GET /daily-summaries/{date}`, `GET /daily-goals/{goalDate}`, `GET /growth/me`)은 앱을 열 때마다 부르는 홈 화면
  API다. 18시에 `GET /growth/me` p95가 805ms라는 것은, 그 시간에 앱을 연 사람 20명 중 1명은 성장 기록이 0.8초 넘게 늦게 뜬다는 뜻이다.
- 인공 요청이 아닌 요청(하루 1,604건) 중에서도 가장 많은 것이 `GET /growth/me`(402건)와 `GET /daily-summaries/{date}`(311건)다.
  이 요청이 실사용자의 것인지 팀원의 시험인지는 확인이 필요하다.

## 결정

### 진행 방식 (사용자 결정)

- **목표는 API 하나가 아니라 전 범위에 하나로 정한다.** API들이 커넥션 풀과 DB를 함께 쓰므로, 한 API만 고치면 병목이 다른
  API로 옮겨 갈 수 있다. 성격이 다른 API에 예외 기준을 둘 수는 있지만, 측정하기 전에 정해 둔다.
- **원인을 먼저 찾고, 병목 순서로 하나씩 고친다.** 잴 때마다 목표를 가장 크게 깨는 원인 하나를 고치고, 같은 시나리오로 다시
  잰다. 여러 개를 한꺼번에 고치면 무엇이 효과가 있었는지 알 수 없다. 목표를 이미 지키는 API는 손대지 않는다.
- **목표 부하에서 기준을 지키면 마친다.** 마지막 측정을 기준선으로 남기고, 이후의 회귀는 하루 요약의 p95 비교로 잡는다.
- 상시 트래픽(Locust)은 지금처럼 두고, 한계 측정은 k6의 열린 모델(`constant-arrival-rate` 등)로 한다. Locust는 서버가 느려지면
  요청도 덜 보내서 지연을 작게 잰다([결정 기록](2026-11-05-locust-over-k6.md)).

### 목표 (제안값, 확정 전)

| 단계 | 조건 | 합격 기준 | 판정 근거 |
|---|---|---|---|
| 1. 지금 부하 | 8,000명 상시 트래픽, 하루 | 모든 API p95 300ms 이하, 커넥션 대기 0 (재시작 직후 5분 제외) | 하루 요약 (서버 기준) |
| 2. 목표 부하 | k6 혼합 요청 **60 RPS**를 30분 유지 | 모든 API **p95 300ms, p99 800ms 이하**, 오류율 0.1% 미만, 커넥션 대기 0 | k6 (클라이언트 기준), 원인 분석은 서버 기준 |
| 3. 여유 | k6 혼합 요청 **120 RPS**를 10분 유지 | 무너지지 않음: 오류율 1% 미만, p99 3,000ms 미만 | k6 (클라이언트 기준) |

- **최종 목표는 2단계와 3단계를 함께 통과하는 것이다.** 1단계는 k6 환경이 정해지기 전에도 확인할 수 있는 중간 목표다.
- k6 측정에서는 목표와 별도로 **한계**도 기록한다. 요청 속도를 계단식으로 올려 p95 300ms가 처음 깨지는 RPS다.
- 혼합 요청의 API별 비율은 11-10 인공 요청의 비율(위 API 표의 요청 수)을 그대로 쓴다.
- 판정에서는 처음 5분을 JVM 워밍업 구간으로 보고 뺀다.

## 근거

| 값 | 근거 |
|---|---|
| 60 RPS | 8,000명의 1분 최대 24.6 TPS × 2.5배(20,000명) ≈ 61. 이 1분 최대는 23시 몰아 기록 세션 구간에서 나왔으므로, 20,000명에서도 페르소나 구성 비율이 지금과 같다는 가정이다. [트래픽 모양과 규모](2026-10-29-traffic-shape.md)가 따로 추정한 20,000명 피크 28-56 RPS와도 크게 다르지 않다 |
| 120 RPS (2배) | 순간 몰림과 데이터 증가에 대한 여유. 가정이다 |
| p95 300ms | 두 가지에서 정했다. ① 부하가 없을 때 가장 느린 `GET /growth/me`도 p95가 111-160ms다(새벽 01-05시). 300ms는 그 약 2배이므로 이미 서버가 낼 수 있는 성능 범위 안이다. ② 홈 화면은 API 3개를 부른다. 사람이 흐름이 끊긴다고 느끼는 1초([Nielsen, Response Times: The 3 Important Limits](https://www.nngroup.com/articles/response-times-3-important-limits/)) 안에 화면이 뜨려면, 네트워크와 화면 그리기 시간을 빼고 API 하나에 300ms 정도가 남는다(추정). 하루 요약의 주의 기준(`MAX_API_P95_MS`)과도 같다 |
| p99 800ms | 지금 p99가 1,000ms를 넘는 API가 있어 꼬리도 따로 묶는다. 1초 안에 들게 한다. 가정이다 |
| p99 3,000ms (3단계) | 거버너가 배율을 낮추는 기준과 같다 |
| 오류율 0.1% | 지금 하루 실패가 0건이므로 엄격하게 둔다. 가정이다 |

버린 선택지:

| 선택지 | 버린 이유 |
|---|---|
| 느린 API마다 목표를 따로 정함 | 공유 자원 때문에 한 API의 개선이 다른 API를 느리게 할 수 있고, 이를 판정하지 못한다 |
| 평균 응답 시간으로 판정 | 지금 문제는 꼬리(p95, p99)에 있다. 평균은 이를 가린다 |
| 지금 부하(25 TPS)만 목표로 함 | 20,000명 단계를 버틸 수 있는지 답하지 못한다 |
| 서버 증설로 해결 | 느려지는 시간대에도 CPU·커넥션 풀·DB에 여유가 있었다. 개선 뒤에도 목표에 못 미치면 다시 검토한다 |

## 이 기록의 한계

- **단계별 비교에는 계정 수 말고도 달라진 것이 있다.** 4,000명 기준선은 주말, 8,000명은 평일이다. 그 사이에 다이어터 추가분
  3,800명과 휴면 직전 200명이 더해졌고, 식사 양을 목표 칼로리로 정하는 변경(11-09)이 들어갔고, 데이터가 며칠 더 쌓였다.
  backend 코드가 바뀌었는지는 확인하지 못했다. 그래서 "계정 수 때문에 느려졌다"고 단정하지 않고, 이유 1과 2(같은 날 안의 비교)를
  주된 근거로 쓴다.
- **백분위는 히스토그램 구간으로 추정한 값이다.** 300ms 부근의 구간 경계는 268ms와 358ms다. 그래서 p95 319ms(`POST /auth/login/dev`)
  처럼 기준에 가까운 값은 실제로 300ms 안일 수도 있다. 기준을 크게 넘는 값(600ms 이상)은 이 오차와 관계없이 넘은 것이다.
- **Prometheus는 1분마다 수집한다.** 1분보다 짧은 순간 몰림은 지표에서 보이지 않는다.
- **하루치 측정이다.** 같은 경향이 다른 날에도 나오는지는 하루 요약으로 계속 본다.
- **인공 계정의 행동은 가정이다.** 시간대별 접속 확률과 세션 구성은 [페르소나 문서](../../docs/personas/)의 가정에서 나왔다. 실제
  사용자의 행동이 다르면 목표 부하(60 RPS)도 달라진다.

## 미결

- **목표 숫자 확정.** 위 값은 제안값이다. 성격이 다른 API(예: `POST /workout-sessions`)에 예외 기준을 둘지도 함께 정한다.
- **k6를 쏠 환경.** 운영 서버가 유일한 환경이다. 운영 서버에 쏘면 실사용자 응답과 버스트 크레딧이 깎이고, 크레딧이 남아 있을 때
  잰 한계는 크레딧이 바닥난 뒤보다 높게 나온다. 선택지는 새벽(02-05시) 운영 서버, 운영 DB를 복사한 별도 환경, 원인 분석을
  먼저 하고 k6를 나중에 하는 순서다. 권장은 마지막이다. 이유 2의 원인 후보는 부하를 더 주지 않고 지금 지표와 쿼리 로그로 먼저
  확인할 수 있다.
- **서비스 저장소 수정은 팀과 함께 한다.** 이 저장소는 k6 시나리오와 측정 기록을 맡는다.
- **16,000명 증량과의 순서.** 전후 비교는 같은 계정 수에서 해야 한다([상시 트래픽을 흘리는 이유](2026-11-09-why-continuous-traffic.md)
  근거 절). 개선 전에 증량할지 정해야 한다.
- **backend 재시작 20회의 원인.** 09:45-17:14에 몰려 있고, 그 시간대 앱 서버 CPU(1시간 최대)가 87-99%였다. 성능 목표와는 별개지만,
  재시작 직후마다 커넥션 대기와 CPU 100%가 생긴다(확인 필요).
- **데이터 서버의 버스트 크레딧.** `t3` 계열이지만 크레딧 설정과 잔량을 확인하지 않았다(확인 필요).

- 하루 숫자는 관측 서버 `alerts` 컨테이너가 남긴 `reports/2026-11-10.json`(하루 요약)이다.
- 시간대별 백분위와 자원(이유 1, 2), 재시작 없는 구간의 백분위, 커넥션 대기 시각, 데이터 서버 CPU, 인공 요청이 아닌 요청은
