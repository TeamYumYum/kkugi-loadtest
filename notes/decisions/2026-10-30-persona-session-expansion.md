# 페르소나와 세션 확장 설계안

| 항목 | 값 |
|---|---|
| 날짜 | 2026-10-30 |
| 상태 | 미결(제안). 아래 "미결"의 사용자 결정을 기다린다 |
| 관련 | [실측 범위](2026-10-29-persona-scope.md), [구현 계획](../plan.md) "이후", 서비스 저장소 `docs/operations/synthetic-traffic.md` 4.1·4.2·6.3절 |

API는 서비스 저장소 `origin/main` `ae844a44`(2026-10-30 15:00 병합)의 `contracts/openapi.json`에서 확인했다.

## 배경

계정 1,000개 실측(2026-10-29 17:07부터 약 22시간)에서 보낸 요청은 다이어터의 식사 기록과 조회 두 세션뿐이었다.

- HTTP 요청 약 21,500건 중 약 3분의 2가 홈 화면 조회(`daily-summaries`, `daily-goals`, `growth/me`)와 토큰 재발급이다. 쓰기는 사진 없는 `POST /meals` 하나다.
- 운동·체중·식사 수정·사진 API의 부하는 한 번도 재지 않았다. 서버의 최대 처리량은 요청이 어떻게 섞였는지에 따라 달라지므로, 이 구성으로 잰 한계값은 실제 사용과 거리가 멀다.

## 결정(제안)

### 1. 순서

세션을 먼저 만들고, 그다음 페르소나를 하나씩 더한다. 세션은 여러 페르소나가 함께 쓰므로, 세션을 갖춰 두면 페르소나 추가는 "어느 세션을 언제 얼마나 고르는가"만 정하면 된다.

1. 공통 세션: 체중 기록, 운동 기록, 식사 수정
2. 다이어터 보강: 식사 수정, 간식, 체중
3. 헬스 입문자 → 꾸준러 → 워치 유저 → 휴면 직전
4. 사진 식사: S3 전환 뒤(6절)

### 2. 새 세션

모든 세션은 지금처럼 홈 화면 3종(`GET /daily-summaries/{date}`, `GET /daily-goals/{date}`, `GET /growth/me`)으로 시작한다. 경로 앞의 `/api/v1`은 생략한다.

**식사 수정(식사 기록 세션 안의 분기).** 서비스 문서 4.2절의 가정대로 식사 기록의 15%가 저장 직후 수정한다.

| 순서 | API | 하는 일 |
|---|---|---|
| 1 | `POST /meals` | 지금과 같다. 응답에서 식사 ID를 얻는다 |
| 2 | `PATCH /meals/{mealId}` | 음식 하나의 양을 바꾼다. 같은 본문을 다시 보내도 결과가 같다 |
| 3 | `GET /daily-summaries/{date}` | 섭취 칼로리가 바뀐 양만큼 달라졌는지 검증한다 |

`PATCH`는 오늘 먹은 식사만 고칠 수 있다(`MEAL_PAST_DAY_LOCKED`). 저장한 세션 안에서 고치므로 걸리지 않는다.

**간식.** 식사 기록 세션을 `mealType=SNACK`으로 쓴다. 끼니 창 밖(예: 14-17시, 20-23시)에 연 세션 일부가 간식 기록이 된다. 확률은 가정이다.

**체중 기록 `weight_log`.**

| 순서 | API | 하는 일 |
|---|---|---|
| 1 | `GET /weight-records/latest` | 현재 몸무게 |
| 2 | `PUT /weight-records/{오늘}` | 오늘 체중. 없으면 201, 있으면 200이다. 하루 여러 번 보내도 한 건이다 |
| 3 | `GET /weight-records?from=..&to=..` | 최근 30일 그래프 |

체중은 시작 체중에서 페르소나별 추세(다이어터는 하루 약 -0.05kg, 가정)에 계정·날짜로 정한 흔들림(±0.5kg, 가정)을 더한다. 재실행해도 같은 값이고, 20-300kg 범위를 벗어나지 않게 자른다.

**운동 기록 `workout`.**

| 순서 | API | 하는 일 |
|---|---|---|
| 1 | `GET /routines` | 내 루틴 전체 |
| 2 | `GET /workout-schedules?from=오늘&to=+7일` | 이번 주 일정 |
| 3 | `GET /exercises?bodyPart=..` | 일부 세션만(가정 30%). 종목 둘러보기 |
| 4 | `POST /workout-sessions` | 끝난 운동 기록. 오늘 일정이 있으면 `scheduleId`로 연결한다 |
| 5 | `GET /weekly-workout-goal/me` | 주간 목표 진행 |

- 업로드 본문은 루틴의 목표에서 만든다. 실제값은 목표에 흔들림을 주고, 일부 세트는 `SKIPPED`로 둔다.
- `endedAt`은 서버 현재 시각 이하여야 하므로 `endedAt = 지금`, `startedAt = 지금 - 운동 시간(40-70분, 가정)`으로 정한다. 세트 완료 시각은 그 사이에 고르게 둔다.
- `clientUuid`는 식사처럼 이메일·날짜·세션 순번으로 정한다. 재실행하면 200(같은 내용)이 오므로 중복 기록이 생기지 않는다.
- 검증: 응답의 세트 수와 완료 세트 수가 보낸 값과 같다.

**운동 준비(세션 전 준비에 추가).** 운동을 하는 페르소나는 처음 한 번 아래를 실행한다. 통계 이름에는 `[setup]`이 붙는다.

1. `GET /exercises`로 종목 목록을 받는다.
2. `GET /routines`가 비어 있을 때만 `POST /routines`로 루틴 1-2개를 만든다. 루틴 생성에는 멱등 키가 없으므로, 목록을 먼저 확인해야 재시도로 루틴이 늘어나지 않는다.
3. `PUT /weekly-workout-goal/me`로 주간 목표(2-4회, 가정)를 정한다.
4. 매주 첫 세션에서 `POST /workout-schedules`로 그 주의 일정을 예약한다.

루틴 ID는 상태 DB에 저장하지 않고 매 세션 `GET /routines`로 읽는다. 앱도 세션마다 루틴 사본을 받으므로 실제 흐름과 같다.

### 3. 페르소나

비중은 서비스 문서 4.1절의 가정값이다. 활동 배수는 이 제안의 가정이다.

| 페르소나 | 비중 | 활동 배수 | 세션 |
|---|---|---|---|
| 다이어터 | 35% | 1.0 | 식사 기록(수정 15%), 간식, 아침 체중(가정 40%), 조회 |
| 헬스 입문자 | 25% | 0.8 | 저녁(18-22시) 운동 주 2-3회, 조회. 목표 `MAINTAIN`·`GAIN` |
| 꾸준러 | 15% | 1.3 | 매일 식사·운동·체중. 23시에 몰아서 기록 |
| 워치 유저 | 15% | 1.0 | 운동 직후 폰이 `POST /workout-sessions`만 올린다. 가끔 조회 |
| 휴면 직전 | 10% | 0.1 | 조회만 |

- **활동 배수 상한:** 설정 검사 규칙은 `가장 큰 시간대 확률(0.5) × 페르소나 배수 × 가장 큰 계정 배수(1.5) ≤ 1`이다. 그래서 페르소나 배수는 1.33을 넘을 수 없다. [실측 범위 기록](2026-10-29-persona-scope.md)의 예시 "꾸준러 1.5"는 이 규칙에 걸리므로 1.3으로 둔다.
- **꾸준러의 23시 몰아 기록:** 공통 표의 23시 확률은 0.1이다. 실측 범위 기록에서 허용한 대로, 꾸준러만 23시 칸을 덮어쓴다. 식사 시각(`eatenAt`)은 오늘 0시부터 지금 사이면 되므로, 23시에 아침·점심·저녁을 각각 그 끼니 시각으로 기록할 수 있다.
- **워치 유저:** 워치는 서버를 모르고 폰이 기록을 올린다(서비스 ADR-0002, ADR-0005). 그래서 요청 흐름은 운동 세션의 4번만 남는다.

### 4. 기존 계정 처리

지금 `persona_of`는 계정 번호로 시드한 난수와 설정의 비중으로 페르소나를 뽑는다. 페르소나를 하나 더하면 기존 계정 다수의 페르소나가 바뀌고, 상태 DB의 페르소나와 어긋난 계정은 `StateStore.load`(`accounts/state.py`)에서 거부되어 매 세션 실패한다.

제안은 두 가지를 함께 바꾸는 것이다.

1. **배정을 고정 구간으로 바꾼다.** 계정 번호의 해시를 0-99로 줄이고, 페르소나마다 구간을 고정한다(다이어터 0-34, 헬스 입문자 35-59, 꾸준러 60-74, 워치 유저 75-89, 휴면 직전 90-99). 아직 구현하지 않은 페르소나의 구간은 다이어터로 둔다. 그러면 지금은 모든 계정이 그대로 다이어터이고, 나중에 한 페르소나를 켜도 그 구간의 계정만 바뀐다.
2. **페르소나가 바뀐 계정은 generation을 올린다.** 탈퇴된 계정에 쓰는 기존 장치를 재사용한다. 새 이메일로 가입하고 새 페르소나의 프로필로 온보딩한다. 옛 회원은 더는 접속하지 않으므로 이탈한 사용자처럼 남는다. 통계에는 `ACCOUNT persona_changed`로 센다.

버린 선택지는 다음과 같다.

- **상태 DB만 지우기:** 서버의 회원은 이미 다이어터 프로필(`LOSE`)로 온보딩했고 온보딩은 다시 할 수 없다(409). 헬스 입문자인데 목표가 감량인 계정이 생긴다.
- **기존 1,000개는 다이어터로 고정:** 계정을 10,000개로 늘리기 전까지 페르소나 비율이 크게 치우친다.

### 5. 트래픽에 주는 영향

- 평균 페르소나 배수가 1보다 작아진다(위 가정값이면 약 0.9). 계정 수가 같으면 세션 수가 약 10% 줄어든다.
- 대신 세션 하나의 요청 수와 쓰기 비율이 늘어난다. 운동 업로드는 본문이 크고 여러 테이블에 쓰므로, 같은 rps라도 DB 부하가 지금보다 크다.
- 페르소나를 켤 때마다 하루 이상 돌려 실측하고, 그다음 페르소나를 켠다. 실측 항목은 [구현 계획](../plan.md) 단계 4와 같다.

### 6. 사진 식사

세션 흐름은 정해 두되 꺼 둔다.

| 순서 | API | 하는 일 |
|---|---|---|
| 1 | `POST /food-recognitions` | multipart `image`. JPEG·PNG·WebP, 10MB 이하 |
| 2 | `GET /food-recognitions/{id}` | 인식 결과. 실패해도 201이고 `status=FAILED`다 |
| 3 | `POST /meals` | `photoRecognitionId`와 후보의 `candidateRank`로 저장. 실패한 인식이면 검색으로 기록한다 |

켜지 않는 이유는 두 가지다.

- **저장 위치:** `origin/main` `ae844a44` 기준으로도 사진 바이트를 업무 DB `meal_photo`에 저장하고 지우지 않는다(`MealPhoto.java`). 서비스 문서 6.3절은 목표 비율이면 하루 약 7.6GB가 쌓인다고 계산하고 "S3로 옮기기 전에는 켜지 않는다"고 정했다.
- **추론 자원:** 인식은 앱 서버의 `ai` 컨테이너가 동기로 처리하므로 backend와 CPU를 나눠 쓴다.

켜는 조건은 S3 전환, 라이선스를 확인한 음식 사진 데이터셋, 낮은 시작 비율(서비스 문서 가정: 세션의 5%)이다.

## 미결

사용자가 정할 것이다.

- 1절의 순서로 진행할지
- 4절의 기존 계정 처리(고정 구간 + generation 올리기)를 채택할지
- 다이어터에게도 가벼운 운동을 섞을지. 서비스 문서 4.1절의 다이어터는 식사만 기록한다
- 3절의 활동 배수와 2절의 확률(모두 가정)
- 사진 S3 전환 일정. 서비스 팀에 확인이 필요하다
