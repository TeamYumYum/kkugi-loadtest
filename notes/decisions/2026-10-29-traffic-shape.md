# 트래픽 모양과 규모

| 항목 | 값 |
|---|---|
| 날짜 | 2026-10-29 |
| 상태 | 일부 대체됨: 세션 시각을 뽑는 방식(→ [시간대별 표](2026-10-29-hourly-table.md)), 시작 규모·관측 서버 사양·동시 세션 수(→ [시작 규모와 관측 서버 부담](2026-10-29-start-scale-and-load.md)). 나머지는 유효 |
| 관련 | 서비스 저장소 `docs/operations/synthetic-traffic.md`(이하 운영 문서) 3·6·7장 |

## 배경

PR #1 머지 시점의 발생기는 `n`을 전체 계정 수로 보고, 계정마다 하루 일정을 만든다. 다이어터의 식사 기록 세션 하나뿐이다.

- 계정 1,000개면 하루 세션 약 2,000개(활동 확률 0.8 × 하루 평균 2.45끼)이고 점심 꼭대기가 약 1 RPS다. 운영 문서의 가정(`n` = 시간당 세션 수 1,000, 하루 약 58,000세션, 꼭대기 28 RPS)과 30배 가까이 차이 난다.
- 식사 시간 창 안에만 세션이 있어 평소 트래픽은 0이고, 창이 열리는 순간 계단처럼 시작된다.
- 이 규모로는 p95·p99(응답 시간 백분위) 표본이 적고, 데이터도 느리게 쌓인다.

## 용어: 톱다운과 보텀업

트래픽을 만드는 방향이 반대인 두 방식이다.

- **톱다운:** 시간대별 전체 목표(예: 12:30에 시간당 10,000세션)를 먼저 정하고, 그만큼 사용자를 무작위로 골라 행동시킨다. 총량은 정확히 맞지만, 한 사용자의 하루가 일관되지 않는다. 같은 사람이 점심을 세 번 기록할 수도 있다.
- **보텀업:** 사용자 한 명 한 명의 하루 일정을 먼저 정한다. 전체 트래픽은 일정의 합으로 나온다. 사용자의 하루는 자연스럽지만, 총량을 원하는 값에 맞추려면 일정을 정하는 규칙을 조정해야 한다.

## 결정

**모델:** 섞어서 쓴다. 일정은 계정마다 정하고(보텀업), 세션 시각을 뽑는 분포를 운영 문서 3장의 곡선에 맞춘다(톱다운의 모양). 모든 계정을 합한 시간대별 세션 수의 기대값이 곡선과 같아지고, 날마다 조금씩 흔들린다.

| 항목 | 값 | 출처 |
|---|---|---|
| 계정 수 | 첫 운영일 10,000, 하루이틀 뒤 20,000 | 사용자 결정 |
| 일반 시간대 활동량 | 시간당 계정 수의 10%가 앱을 연다 (1,000 → 2,000) | 사용자 결정. "활동"은 동시 세션 수가 아니라 시간당 앱을 여는 계정 수로 해석했다 |
| 밤 시간대 | 일반 시간대의 1/10 | 사용자 결정 |
| 계정별 세션 수 | 계정마다 활동 성향 배수(평균 1)를 두어 평균은 맞추고 편차를 둔다 | 사용자 결정 |
| 밤의 범위 | 01:00~06:00, 경계는 완만하게 바꾼다 | 가정 |
| 피크 | 일반 시간대의 10배, 중심 07:30·12:30·18:30, 표준편차 30분 | 가정 (운영 문서 3장 값) |

## 근거

- **계정 수를 늘리고 계정당 빈도는 현실적으로 둔다.** 같은 트래픽을 한 계정이 하루 열 끼를 기록해서 만들면 요약·성장 데이터가 비현실적으로 바뀐다. 계정을 늘리는 비용은 발생기에서 작다(계정 하나는 SQLite 한 행과 하루 일정 몇 개다). 부담은 backend의 회원·식사 데이터와 Redis 리프레시 토큰 쪽에 생기는데, 이것은 관찰하려던 대상이기도 하다.
- **모양은 계정 수가 아니라 세션 시각 분포가 정한다.** 계정 수를 늘리면 크기만 비례해서 커진다. 그래서 곡선을 세션 시각 분포에 반영한다.
- **"평소에는 일부 계정만 켠다"는 장치를 따로 두지 않는다.** 세션 시각을 곡선에서 뽑으면 평소 시간대의 활동 계정 수는 결과로 나온다.
- **한계 측정은 상시 트래픽이 맡지 않는다.** 운영 서버가 유일한 환경이라 상시 트래픽을 한계까지 올리면 실사용자 응답과 CPU 크레딧(Lightsail이 기준 사용률을 넘을 때 쓰는 성능 예산)이 계속 깎인다. 또 Locust는 서버가 느려지면 요청도 덜 보내 지연이 작게 측정된다. 처리량 한계는 운영 문서대로 k6 부하 테스트(B)에서 찾는다. 상시 트래픽이 드러내는 한계는 데이터가 쌓이며 생기는 것(느려지는 쿼리, 테이블·백업 크기, 장시간 운영 중 누수)이다.
- **계정 수는 자동 가입과 수동 상한으로 늘린다.** 새 계정이 날마다 활성화되되, 활성 계정 상한은 사람이 운영 문서 7.2절 기준을 확인한 뒤에만 올린다. 그 사이에 서버가 버거우면 거버너(실패율·p99를 보고 배율을 자동으로 낮추는 장치)가 보호한다.

버린 선택지:

| 선택지 | 버린 이유 |
|---|---|
| 운영 문서의 톱다운 곡선을 그대로 구현 | 한 사용자의 하루가 일관되지 않아 데이터 축적이라는 목적과 맞지 않는다 |
| 계정당 기록 횟수를 늘려 양을 맞춤 | 비현실적인 사용자 데이터가 생긴다 |
| 상시 트래픽으로 한계를 찾음 | 위 근거 참고 |

## 결과

계정 20,000개 기준 추정치다. 가정이 바뀌면 비례해서 바뀐다.

| 항목 | 값 |
|---|---|
| 하루 세션 수 | 약 107,000 |
| 계정 1개의 하루 평균 세션 | 약 5.4회. 자주 여는 계정과 드물게 여는 계정으로 나뉜다 |
| RPS (세션당 5~10요청 가정) | 일반 3~6, 피크 28~56, 밤 0.3~0.6 |
| 피크 동시 세션 수 | 약 1,000 (세션 3분 가정). 실행기 User 수(`-u`)는 1,200쯤으로 둔다 |
| 운영 문서 가정 대비 | 약 1.8배. 월 전송량은 JSON만 약 160GB로 허용량 4TB보다 작다 |

계산식: 하루 세션 수 ≈ 기준값 B × (일반 19시간 + 밤 5시간 × 0.1 + 봉우리 세 개 × 11.3) ≈ 53.5B. 봉우리 하나가 더하는 양 11.3은 `(10 − 1) × 0.5 × √(2π)`이다. B = 2,000이면 약 107,000이다.

주의할 점:

- 계정당 하루 5.4회는 높은 편이다. 피크 배수를 5배로 낮추면 하루 약 69,000세션, 계정당 약 3.5회가 된다.
- 운영 문서 7.2절은 n=100으로 하루 실측한 뒤에 올리라고 한다. 첫날 10,000개로 시작하면 이 단계를 건너뛰므로, 거버너와 정지 스위치가 먼저 있어야 한다.
- 운영 서버의 dev 로그인이 아직 꺼져 있다. 실제 첫 운영일은 발생기 쪽 준비와 backend 작업(구분 헤더, dev 로그인 활성화)이 끝난 날이다.

## 미결

- 피크 배수: 10배(가정) 유지 또는 5배로 낮춤
- 밤의 범위: 01:00~06:00(가정)
- 운영 문서의 `n` 정의와 3·6장 산정을 이 결정에 맞게 고칠지, 누가 고칠지. 문서 소유자는 인프라 담당이다
- 관측 서버 사양: 운영 문서는 Medium 4GB, 이전 인계 문서는 Large 8GB를 전제로 했다. 확인 필요
