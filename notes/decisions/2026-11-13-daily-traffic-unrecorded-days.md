## 한눈에 보기

- **무엇을 남기나.** 발생기는 10-29부터 쉬지 않고 돌았는데, 기준선 기록은 계정 수를 늘린 직후의 며칠만 다뤘다. 그 사이에 하루치
  숫자가 어디에도 남지 않은 날이 엿새 있었다. Prometheus 지표는 2주 뒤에 사라지므로, 사라지기 전에 같은 방법으로 재서 남긴다.
- **4,000명 평일(11-05, 11-06).** 하루 HTTP 요청 약 12.1만-12.3만 건, 세션 약 15,800건, 평균 1.41-1.42 TPS다. 주말 기준선
  (11-07, 11-08의 1.39 TPS)과 같다. 일정에 요일 구분이 없기 때문이다.
- **8,000명 평일(11-11, 11-12).** 하루 HTTP 요청 약 22.3만-22.6만 건, 세션 약 31,000-31,400건, 평균 2.58-2.62 TPS다.
  11-10(228,513건, 2.644 TPS)과 같다.
- **섞인 날(11-04, 11-09).** 11-04는 09:05에 2,000명에서 4,000명으로, 11-09는 14:56에 4,000명에서 8,000명으로 바뀌었다. 두 날의
  값은 단계끼리 비교하는 데 쓰지 않는다.
- **실패.** 엿새 동안 HTTP 실패는 51건이고 놓친 세션은 0건이다. 11-04의 43건은 backend가 재시작하던 시간의 502와 연결 실패,
  11-09의 7건은 `POST /workout-sessions`의 500, 11-12의 1건은 backend 재시작 직후의 연결 실패다.

## 용어

용어는 [용어집](../../docs/glossary.md)을 따른다. 이 기록에서 "기록 시간"은 그날 Locust 통계 기록이 이어진 시간의 합이다.
Master가 멈춰 기록 사이가 180초 넘게 벌어진 구간은 여기서 빠진다.

### Master를 다시 시작한 날의 보정

Locust는 Master를 시작할 때 누적값을 0으로 되돌리고 새 CSV를 쓴다. 위 표의 규칙은 기록과 기록 사이의 증가분만 세므로,
Master를 시작한 뒤 첫 기록이 남기까지 약 1분 동안 보낸 요청이 빠진다. 다시 시작한 직후에는 밀린 세션을 한꺼번에 실행하므로
이 1분의 요청이 많다. Master 시작 시점의 누적값을 0으로 놓고 더하면 아래와 같고, backend가 센 인공 요청 수와 맞는다.

| 날짜 | Master 시작 | 위 표의 HTTP 요청 / 세션 | 첫 1분을 더한 HTTP 요청 / 세션 | backend가 센 인공 요청 |
|---|---|---:|---:|---:|
| 11-04 | 09:05 | 117,586 / 13,340 | 119,380 / 13,694 | 119,574 |
| 11-09 | 11:14, 11:38, 14:57 | 158,196 / 21,062 | 163,213 / 21,788 | 163,193 |

- Master를 다시 시작하지 않은 나흘은 Locust 값과 backend 값의 차이가 3-117건이다(11-05 122,936 / 122,933, 11-06 121,351 /
  121,234, 11-11 226,457 / 226,450, 11-12 222,821 / 222,798).
- 첫 1분을 더하면 1분 최대 TPS는 11-04가 29.9(09:06), 11-09가 34.2(14:58)다. 밀린 세션을 한꺼번에 실행한 값이라 평소의
  봉우리로 보지 않는다.
- 이 기록의 나머지 표는 다른 날의 기록과 같은 규칙을 쓴 위 표의 값을 따른다.

## 다시 재는 방법

- **날짜마다 그날을 덮는 CSV를 모두 쓴다.** 11-04는 `kkugi-20261102-152235`(09:05:00까지)와 `kkugi-20261104-090514`(09:05:22부터),
  11-09는 `kkugi-20261104-090514`(11:14:39까지), `kkugi-20261109-111459`, `kkugi-20261109-113822`, `kkugi-20261109-145702`다.
  나머지 날은 CSV 하나다.
- **CSV마다 따로 증가분을 구해 더한다.** 누적값이 Master 시작마다 0으로 돌아가므로 CSV를 이어 붙이면 안 된다. 규칙은
  `tools/daily_report.py`의 `traffic()`과 같다. 그날 구간의 기록만 세고, 180초 넘게 벌어진 기록 사이는 뺀다. 이 계산은 저장소
  밖의 임시 스크립트로 했다. `tools/daily_report.py`는 CSV 하나만 받는다.
- **계산을 두 가지로 확인했다.** CSV가 하나인 11-10, 11-11, 11-12는 관측 서버의 하루 요약 JSON과 HTTP 요청, 세션, 평균 TPS,
  1분 최대 TPS가 모두 같다. 엿새 모두 backend가 센 인공 요청 수(`http_server_requests_seconds_count{synthetic="true"}`의 하루
  증가분)와 비교했다.
- 서버 기준 값은 `tools/daily_report.py`의 `server()`를 그대로 썼다. 노트북에서 `ssh -N -L 19090:localhost:9090 kkugi-obs`
  터널로 Prometheus를 열었다.
- 커넥션 대기가 생긴 분은 `max(max_over_time(hikaricp_connections_pending[1m]))`를 60초 간격으로 조회했다.
- 실패 시각은 history CSV에서 `Total Failure Count`가 늘어난 기록의 시각이고, 오류 내용은 `_failures.csv`다.
