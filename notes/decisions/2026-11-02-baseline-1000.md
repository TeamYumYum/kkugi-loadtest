# 기준선: 다이어터 1,000명의 TPS·세션/s·DB TPS

| 항목 | 값 |
|---|---|
| 날짜 | 2026-11-02 |
| 상태 | 결정 |

## 배경

계정 수를 2배씩 늘리기 전에([증량 순서](2026-11-02-account-ranges-and-ramp.md)) 지금 구성의 처리량을 재 둔다.
단계마다 같은 방법으로 다시 재서 이 값과 비교한다.

측정할 때 TPS의 뜻이 사람마다 달라 혼란이 있었다. 그래서 용어를 먼저 정했다.

## 결정

**용어(사용자 결정).** README의 "사용자와 부하 모델" 표에 정의를 적었다.

| 이름 | 뜻 | 보는 곳 |
|---|---|---|
| TPS (= RPS) | 초당 HTTP 요청 수. 로그인·토큰 재발급·온보딩 포함 | Locust 통계 기록의 HTTP 요청 줄 |
| 세션/s | 초당 끝난 업무 세션 수. 건너뛴 `(skipped)` 세션 제외 | Locust 통계 기록의 `SESSION` 줄 |
| DB TPS | 초당 MySQL 커밋 수 | Prometheus `mysql_global_status_commands_total{command="commit"}` |

TPS라고만 쓰면 HTTP 요청 기준이다. nGrinder에서 요청 하나를 테스트 하나로 두는 흔한 방식과 JMeter의 샘플러 기준
처리량이 이 뜻이라, 다른 사람이 읽을 때 오해가 적다. 세션은 JMeter의 Transaction Controller에 해당하지만 우리
세션 시간에는 생각 시간이 들어 있어 서버 성능보다 업무 완료량을 보는 지표로 쓴다.

## 결과

**측정 조건.** 관측 서버의 발생기는 PR #3 상태(`d926680`)다. 다이어터 1,000명(0-999번), Worker 2개, 배율 1.0,
`KKUGI_USERS=10`. PR #4~#6(체중·식사 수정·운동 세션, 운동 초보자)은 배포 전이다. 기준 시각은 2026-11-02 14:58(KST).

**평균.**

|---|---:|---:|---:|
| 최근 1시간 (13:58-14:58, 평시) | 0.106 | 0.026 | 0.078 |
| 최근 24시간 | 0.282 | 0.047 | 0.274 (아래 두 구간을 빼면 약 0.20) |
| 최근 72시간 | 0.275 | 0.045 | 0.254 |

**시간대별 (2026-11-01 15시 ~ 11-02 14시, KST).**

|---|---:|---:|---:|
| 새벽 01-05시 | 0.004-0.015 | 0.001-0.004 | 0.003-0.010 |
| 평시 09-10, 14-16, 20-23시 | 0.10-0.13 | 0.025-0.033 | 0.05-0.09 |

**실패.** 72시간 동안 HTTP 요청 12건(0.02%), 최근 24시간 0건.

**값이 이 정도인 이유.** 계정 하나가 하루에 앱을 여는 기대 횟수는 `open_probability` 24칸의 합인 4.05회다.
1,000명이면 하루 약 4,050개 세션(실측 4,033개)이고, 세션 하나에 요청이 약 6개라 하루 약 24,400개 요청,
평균 0.28 TPS다. 상시 시뮬레이션은 사용자 1,000명의 하루를 재현하는 것이고 최대 처리량 측정이 아니다.

**DB TPS에서 따로 볼 구간.** DB TPS는 backend 전체 기준이라 발생기가 보내지 않은 작업도 들어간다.

| 시각 | DB TPS (1분) | 추정 원인 |
|---|---:|---|
| 11-02 00:01 | 55.6 | HTTP 요청은 평시와 같았다. backend의 자정 배치 작업으로 보인다(확인 필요) |
| 11-02 11:23-11:24 | 22.1, 17.3 | 발생기 밖의 인공 요청 약 1,800건이 같은 시간에 있었다. 배포 전 확인 실행으로 보인다(확인 필요) |

두 구간을 빼면 요청 하나당 DB 커밋은 약 0.75개다. 조회 요청 일부는 커밋 없이 끝난다. 요청 하나는 저장소 호출
약 3.7회, `SELECT` 약 4.4개를 보낸다(24시간 평균, 위 구간 포함).

**다시 재는 방법.**

- TPS·세션/s: Master의 `kkugi-<시작 시각>_stats_history.csv`에서 이름별 `Total Request Count`의 구간 증가분을
  구간 초로 나눈다. 종류(`Type`)가 `SESSION`·`SCHEDULE`·`ACCOUNT`가 아닌 줄이 HTTP 요청이다.
- DB TPS: `sum(rate(mysql_global_status_commands_total{command="commit"}[1h]))`. 교차 확인용 backend TPS는
  `sum(rate(http_server_requests_seconds_count{synthetic="true"}[1h]))`다.
