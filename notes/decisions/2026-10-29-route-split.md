# 요청 경로 분할은 공인 경로 전용 Worker로 한다

| 항목 | 값 |
|---|---|
| 날짜 | 2026-10-29 |
| 상태 | 결정 |
| 관련 | [구현 계획](../plan.md) 3-1, 서비스 저장소 `docs/operations/synthetic-traffic.md` 2.1절 |

## 배경

서비스 저장소의 운영 문서가 요청의 95%는 앱 서버 프라이빗 IP로, 5%는 공인 주소로 보내기로 정해 두었다(2026-10-28). 프라이빗 경로는 발생기 컨테이너에서 도메인을 앱 서버 프라이빗 IP로 매핑해 443으로 연결한다. 도메인 이름으로 연결하므로 인증서 검사가 그대로 통과하고, 80 포트로 IP만 지정하면 HTTPS로 리다이렉트(301)되어 쓸 수 없다. 계획에는 두 방식이 남아 있었다.

- (가) 공인 경로 전용 Worker 컨테이너를 따로 두고 계정 5%를 맡긴다
- (나) 한 Worker 안에서 세션마다 경로를 고른다

## 결정

- **(가)로 한다.** 상시 Worker를 둘로 나눈다.
  - 프라이빗 Worker: 도메인을 앱 서버 프라이빗 IP로 매핑한 컨테이너(compose `extra_hosts`). 계정 풀 `base`
  - 공인 Worker: 매핑 없는 컨테이너. 계정 풀 `public`
- 두 Worker의 대상 주소는 같은 `https://<도메인>`이다. 차이는 컨테이너의 이름 해석뿐이다.
- 계정 풀은 `base` 0-949, `public` 950-999로 나눈다(계정 1,000개, 5%). 계정 수를 늘릴 때 두 풀을 같은 비율로 함께 늘린다.
- 공인 Worker의 HTTP 요청 통계 이름에는 경로 표시를 붙여 경로별 응답 시간을 나눠 본다. 세션·일정 통계는 나누지 않는다.

## 근거

- 도메인 매핑은 컨테이너 전체에 걸리므로, 한 컨테이너 안에서 세션마다 경로를 고르려면(나) 이름 해석을 요청 단위로 바꾸는 연결 설정을 직접 만들어야 한다. (가)는 compose 설정만으로 된다.
- 계정 단위로 나누면 같은 계정은 늘 같은 경로로 간다. 실제 사용자도 한 기기에서 한 경로로 들어오므로 어색하지 않다.
- 팀원 노트북 Worker는 바깥에 있어 자연히 공인 경로로 간다. 피크 시간대에는 공인 경로 비중이 5%보다 커진다.

## 결과

- Master는 User를 Worker 수대로 고르게 나누므로 공인 Worker도 프라이빗 Worker와 같은 수의 User를 받는다. 필요 실행기 수는 프라이빗 Worker 기준으로 맞추고, Master의 User 수는 그 두 배 이상으로 둔다. 노트북 Worker가 붙으면 세 배 이상이다.
- 계정 상태 DB는 Worker마다 따로 둔다. 두 Worker의 계정 범위가 겹치지 않으므로 옮길 일이 없다.
