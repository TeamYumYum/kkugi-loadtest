## 요약

- **문제**: 초당 7-8건이라는 적은 요청에서 홈 화면 API가 새벽(유휴)보다 크게 느려진다. 18시의 p50은 `GET /growth/me`가 7배,
  `GET /daily-goals/{goalDate}`가 24배다. 그때 CPU와 DB는 대부분 비어 있었다. 요청이 많아서 느린 것이 아니라 **느리면 안 되는
  조건에서 느려지는 결함**으로 본다.
- **원인 (1차 분석)**: `GET /growth/me` 한 번이 커넥션을 5-8번 따로 얻고 DB와 25-40번 왕복해, 요청 하나가 커넥션을 약 95ms
  붙잡는다. 그래서 요청 50건이 한순간에 들어오면 커넥션 풀 10개를 차례로 기다리느라 마지막 요청이 약 475ms 늦어진다. 발생기는
  세션을 매분 0초에 시작해 이런 몰림을 만드는데, 몰림은 원인이 아니라 약점을 드러낸 조건이다. 1초에 50건은 합격선(초당 60건)보다
  작은 부하이고, 알림처럼 실제로도 생길 수 있다. **고칠 곳은 서버다**("원인 분석" 절).
- **할 일**: ① 저부하 지연의 원인을 찾아 없앤다(결함 해결). ② k6로 어디까지 버티는지 잰다(한계 확인). ③ 한계가 서비스가 가정한
  20,000명에 모자랄 때만 성능 개선을 한다.
- **이번 범위는 ①뿐이다(사용자 결정, 2026-11-11).** ②와 ③은 보류하고, 필요해지면 새 기록으로 시작한다.
- **이번 범위가 끝나는 조건**: 8,000명 상시 트래픽에서 모든 API p95 300ms 이하, 커넥션 대기 0이고(합격선 A), 홈 화면 API의 봉우리
  시간 p95가 새벽 p95의 2배 안에 든다(최선 기준 ①을 상시 트래픽으로 판정). 자세한 것은 "이번 범위와 끝나는 조건" 절에 있다.
- **아직 정하지 않은 것**: 목표 숫자 확정, 16,000명 증량과의 순서, 앱이 홈 화면 API를 부르는 방식.

## 배경

꾸기는 식단·운동 기록 앱이다. 이 저장소의 발생기는 인공 계정으로 운영 서버에 현실적인 하루를 흉내 낸 요청을 계속 보낸다. 짧은
부하 테스트로는 드러나지 않고 회원 수와 쌓인 데이터에서만 드러나는 문제를 실사용자보다 먼저 겪기 위해서다
([상시 트래픽을 흘리는 이유](2026-11-09-why-continuous-traffic.md)). 계정 수는 2,000 → 4,000 → 8,000 → 16,000 → 20,000으로
2배씩 늘리고, 단계마다 하루 이상 지켜본다. 20,000명은 이 서비스가 가정한 사용자 규모다(사용자 설명).

8,000명 단계가 처음으로 하루(2026-11-10 화요일, 한국 시간 00:00-24:00)를 채웠다. 다음 날 하루 요약(`tools/daily_report.py`)에
API 8개의 p95가 300ms를 넘었다는 주의가 붙었다. 사용자는 "유의미하게 느린 게 맞다"고 판단했다.

처음에는 이 일을 "성능 개선"으로 정의했다. 그런데 시간대별로 나눠 보니 요청이 적은 시간에도 자원은 남는 채로 느려지고 있었다.
그래서 "더 빠르게 만드는 일"이 아니라 "느리면 안 되는데 느려지는 결함을 없애는 일"로 다시 정의했다(사용자 결정, 2026-11-11).

## 문제: 느리면 안 되는데 느려진다

### 1. 초당 7-8건에서 몇 배씩 느려진다

같은 날 같은 서버에서, 요청이 거의 없는 새벽과 요청이 몰리는 시간대를 비교했다. backend 재시작이 없던 시간대만 골랐다.
응답 시간은 서버 기준(ms)이고, TPS는 발생기 기록이다.

| 시 | TPS | `GET /growth/me` p50 / p95 | `GET /daily-goals/{goalDate}` p50 / p95 |
|---|---:|---:|---:|
| 03시 (유휴) | 0.08 | 52 / 115 | 6 / 12 |
| 07시 (아침 봉우리) | 6.53 | 207 / 452 | 101 / 310 |
| 18시 (저녁 봉우리) | 7.89 | 380 / 805 | 145 / 447 |
| 23시 (몰아 기록 세션) | 9.56 | 102 / 764 | 9 / 326 |

### 2. 그때 어떤 자원도 차지 않았다

| 시 | JVM CPU 평균 | 앱 서버 CPU 평균 | 커넥션 풀 최대 사용 | 커넥션을 얻는 데 걸린 평균 시간 | 데이터 서버 CPU 평균 | MySQL 행 잠금 대기 |
|---|---:|---:|---:|---:|---:|---:|
| 03시 | 0.3% | 2% | 0/10 | 0.6ms | 44% (주) | 0회 |
| 07시 | 2.0% | 5% | 3/10 | 26ms | 4% | 6회, 합계 27ms |
| 18시 | 10.8% | 19% | 5/10 | 4.7ms | 11% | 1회, 합계 9ms |
| 23시 | 14% | 25% | 10/10 | 1.5ms | 10% | 1회, 합계 125ms |

주: 03시에는 요청이 거의 없으므로 backend와 무관한 데이터 서버 작업으로 보인다(확인 필요).

- CPU와 DB에는 여유가 있었다.
- **커넥션 풀은 평균으로는 비어 있었지만 순간적으로는 찼다.** 위 표의 "최대 사용"은 1분에 한 번 찍은 값이라 1분보다 짧은 몰림을
  놓친다. 누적 값으로 보면 07시 한 시간 동안 커넥션을 쓴 시간의 합은 775초(평균 0.2개)인데, 커넥션을 기다린 시간의 합은 1,722초였다
  (`hikaricp_connections_usage_seconds`, `hikaricp_connections_acquire_seconds`). 짧은 순간에 요청이 몰려 풀이 다 찼다는 뜻이다.
- **앱 서버가 낼 수 있는 양은 지금보다 훨씬 크다(추정).** 07시에 backend는 23,352건을 처리하며 JVM CPU를 평균 2.0% 썼다. 2코어
  기준으로 요청 하나에 CPU 약 6ms다(0.020 × 2코어 × 3,600초 ÷ 23,352건). 다른 일도 섞인 값이므로 실제 요청 비용은 이보다 작다.
  이 비용이면 2코어로 초당 약 320건(100% 사용), 여유를 두면 약 230건(70% 사용)을 처리할 수 있다. 초당 7-8건은 그 2-3%다.

### 3. 그래서 병목이 아니라 경합으로 본다

병목은 어떤 자원이 꽉 차서 생기는 줄이다. 여기서는 CPU와 DB가 남았고, 커넥션 풀만 짧은 순간에 찼다. 자원은 남는데 요청들이
커넥션을 차례로 기다리는 상태, 즉 **경합**이다. 왜 그렇게 되는지는 아래 "원인 분석" 절에 있다.

### 4. 계정이 늘 때마다 더 나빠지고 있다

| 지표 | 2,000명 저녁 | 4,000명 주말 | 8,000명 (11-10) |
|---|---:|---:|---:|
| 하루 평균 TPS | 0.49 | 1.39 | 2.64 |
| 18시 TPS (1시간 평균) | 1.78 | 3.64 | 7.89 |
| `GET /growth/me` p50 / p95 (하루) | 29.7 / 76.4 | 67.9 / 152.1 | 178.1 / 632.8 |
| `GET /daily-goals/{goalDate}` p95 (하루) | 17.2 | 53.1 | 347.3 |
| `POST /workout-sessions` p95 (하루) | 153.1 | 227.0 | 514.5 |
| 커넥션 풀 최대 사용 / 대기 | 3/10, 0 | 3/10, 0 | 10/10, 62 |

요청 수는 단계마다 약 2배가 되었는데, p95는 2-6배가 되었다. 다만 이 비교에는 계정 수 말고도 달라진 것이 있다("이 기록의 한계").
그래서 이 표는 보조 근거로만 쓰고, 주된 근거는 같은 날 안에서 비교한 1과 2다.

### 5. 사용자가 기다리는 화면이다

- 가장 느린 API 셋(`GET /daily-summaries/{date}`, `GET /daily-goals/{goalDate}`, `GET /growth/me`)은 앱을 열 때마다 부르는 홈
  화면 API다. 18시에 `GET /growth/me` p95가 805ms라는 것은, 그 시간에 앱을 연 사람 20명 중 1명은 성장 기록이 0.8초 넘게 늦게
  뜬다는 뜻이다.
- 앱은 세 API를 동시에 부를 수 있을 것으로 본다(사용자 설명, 확인 필요). 동시에 부르면 화면이 다 뜨는 시간은 가장 느린 API에
  맞춰지고, 차례로 부르면 세 API의 합이 된다.
- 인공 요청이 아닌 요청(하루 1,604건) 중에서도 가장 많은 것이 `GET /growth/me`(402건)와 `GET /daily-summaries/{date}`(311건)다.
  이 요청이 실사용자의 것인지 팀원의 시험인지는 확인이 필요하다.

### 6. 고치지 않으면

계정은 20,000명까지 늘어난다. 지금의 2.5배다. 지금도 초당 7-8건에서 p95가 800ms에 이르므로, 그대로 두면 다음 단계에서 사람이
기다림을 느끼는 1초를 넘을 것으로 본다(추정). 서버를 키워도 풀리지 않는다. 자원이 모자라서 생긴 지연이 아니기 때문이다.

## 원인 분석 (1차, 2026-11-11)

추적(Tempo)으로 `GET /growth/me` 요청을 열어 시간이 어디에 쓰였는지 보았다. 요청이 한순간에 몰리는 조건(가)에서, 요청 하나가
커넥션을 오래 붙잡는 서버의 약점(나)과 작은 풀(다)이 지연을 만든다. 지연의 크기를 정하는 것은 나다("계산" 절).

### 가. 드러낸 조건: 요청이 매분 0초에 몰린다

세션 시각은 `kkugi_load/personas/base.py`의 `open_times`가 `time(hour, 분)`으로 만든다. 초가 없으므로 모든 세션이 매분 0초에
시작하고, 세션의 첫 요청인 홈 화면 API 3개가 그 순간에 함께 나간다. 운동 세션 시각(`personas/workout_plan.py`)도 분 단위다.

07:14:50-07:17:10의 `GET /growth/me` 추적 152건이 이를 보여 준다.

| 시작 시각 | 요청 수 | 걸린 시간 중앙값 | 최대 |
|---|---:|---:|---:|
| 07:15:00 | 44 | 221ms | 501ms |
| 07:15:01 | 6 | 110ms | 133ms |
| 07:16:00 | 47 | 179ms | 365ms |
| 07:17:00 | 54 | 172ms | 474ms |
| 07:17:01 | 1 | 94ms | 94ms |

**모든 요청이 매분 0-1초에 몰렸다.** 이 몰림은 지연의 원인이 아니라 약점을 드러낸 조건으로 본다(사용자 판단, 2026-11-11).

- 1초에 약 50건은 합격선(초당 60건)보다 작은 부하다. 서버는 이 정도를 견뎌야 한다.
- 알림을 한꺼번에 보내면 실제 사용자도 같은 순간에 앱을 연다. 몰림은 실제로도 생긴다.
- 분의 0초에 맞춰 시작하는 모양 자체는 현실적이지 않다. 이것은 결함을 고친 뒤 발생기의 현실성 문제로 따로 다룬다("미결").

### 나. `GET /growth/me` 한 번이 커넥션을 여러 번 얻고 DB와 수십 번 왕복한다

서비스마다 트랜잭션을 따로 열고 닫는 순서는 [시퀀스 다이어그램](../figures/growth_me_sequence.png)
([Excalidraw 원본](../figures/growth_me_sequence.excalidraw))에 있다. 2026-11-11 07:15 추적 40건 기준으로 요청 하나가 커넥션을
보통 6-7번, 뱃지를 줄 때 12번 빌린다. 11-10에 들어온 PR 뱃지 조회가 단계를 늘렸다. 그림의 화살표마다 소요 시간 중앙값을 적었다.

커넥션을 7번 빌린 요청을 추적에서 골라 시간을 나눴다(중앙값, ms).

| 구간 | 요청 하나 전체 | 커넥션 대기 | DB 문장 39개 | 그 밖 (Java 처리) |
|---|---:|---:|---:|---:|
| 유휴 (11-11 02-05시, 34건) | 88.6 | 0.8 | 83.8 | 4.0 |
| 몰림 (11-11 07:10-07:25, 30건) | 325.3 | 221.3 | 98.5 | 6.1 |

- DB 문장 하나는 유휴 때 약 2ms, 몰림 때 약 2.5ms다. 39개 중 쿼리는 11개이고 나머지 28개는 트랜잭션 관리 문장이다.
- 몰림 때 늘어난 시간은 거의 모두 커넥션 대기다. 대기는 요청마다 ①-⑦ 중 다른 단계에서 생긴다. 단계별 평균은 78.7, 35.9, 29.4,
  13.3, 25.5, 21.2, 16.1ms이고, 합이 220ms다.

같은 API의 두 요청을 비교했다.

| 요청 | 전체 | 커넥션 얻기 | 트랜잭션 관리 문장 (SET, COMMIT) | 쿼리 |
|---|---:|---:|---:|---:|
| 07:17:00 (몰림) | 474ms | 8번, 348ms | 27번, 72ms | 14번, 41ms |
| 03시 (유휴) | 100ms | 5번, 1ms | 16번, 73ms | 9번, 22ms |

- 몰린 요청은 시간의 73%(348ms)를 커넥션을 기다리는 데 썼다. 실제 쿼리는 41ms였다.
- 요청 하나가 커넥션을 5-8번 따로 얻는다. 온보딩 확인, 뱃지 미지급 조회, 성장 기록 조회, 뱃지 조건 확인(식사·운동 기록 조회),
  처리 잠금 행 준비, 뱃지 지급, 요약 조회가 각자 커넥션을 빌린다. `@Transactional`이 붙은 메서드는 Spring이 autocommit을 끄고
  COMMIT으로 끝내는 DB 트랜잭션을 하나씩 열고, 붙지 않은 호출은 autocommit이라 문장 하나가 곧 DB 트랜잭션이다(서비스 저장소 `GrowthController`, `BadgeAwarder`,
  `GrowthQueryService`). 조회 API지만 요청마다 뱃지 지급을 먼저 시도한다.
- `@Transactional` 메서드마다 읽기 전용 설정, 자동 커밋 끄기·켜기, 커밋 같은 관리 문장이 오간다. 이것이 실제 쿼리보다 많고, 시간도 더 든다.
  유휴 때의 100ms도 대부분 이 왕복이다.
- 문장 하나에 1-5ms가 든다. 앱 서버와 데이터 서버가 서로 다른 클라우드에 있어 왕복마다 네트워크 시간이 붙는다(추정, 따로 재지 않음).

### 다. 커넥션 풀이 10개다

매분 0초에 약 50개 세션이 홈 화면 API를 보내고, 그중 `GET /growth/me` 하나가 커넥션을 5-8번 얻는다. 풀 10개로는 그 순간을
감당하지 못해 줄이 생긴다. 평균 사용은 0.2개뿐이라 1분 단위 지표에서는 보이지 않았다.

### 계산: 몰림이 지연으로 바뀌는 양

요청 N건이 한순간에 들어와 커넥션 P개를 나눠 쓰면, 마지막 요청은 대략 `N ÷ P × (요청 하나가 커넥션을 붙잡는 시간)`만큼 기다린다.
몰리면 어느 정도 기다리는 것은 피할 수 없지만, 그 크기는 서버가 커넥션을 붙잡는 시간이 정한다.

| 경우 | 요청 하나가 커넥션을 붙잡는 시간 | 50건이 몰릴 때 마지막 요청의 대기 |
|---|---:|---:|
| 지금 (03시 추적 실측) | 약 95ms (관리 문장 73ms + 쿼리 22ms) | 50 ÷ 10 × 95ms ≈ 475ms |
| 트랜잭션 하나에 쿼리 몇 개로 줄인 경우 (가정) | 약 20ms | 50 ÷ 10 × 20ms ≈ 100ms |

계산한 475ms는 몰림 때 관측한 최대값(474-501ms)과 맞는다. 그래서 **고칠 곳은 나(요청 하나가 커넥션을 붙잡는 시간)이고, 다(풀
크기)는 그다음이다.** 풀만 키우면 데이터 서버에 동시 연결이 늘 뿐 요청 하나의 비용은 그대로다.

### 분석의 한계와 남은 확인

- 추적은 `GET /growth/me` 두 건을 자세히 보았다. 다른 홈 화면 API(`GET /daily-summaries/{date}`, `GET /daily-goals/{goalDate}`)도
  같은 모양인지 확인해야 한다.
- 계산은 몰린 요청이 모두 `GET /growth/me`와 같은 비용이라고 단순화했다. 실제로는 세 API가 세션마다 차례로 나간다.
- 저녁 지연(18시 `GET /growth/me` p95 805ms)에도 같은 원인이 작동하는지는 아직 보지 않았다. 저녁에는 마지막 끼니 배치가 커넥션을
  함께 쓴다(18시 커넥션 얻기 약 60만 번).

### 진행 방식 (사용자 결정)

- **팀과 합의한 작업이다.** 서버 코드는 서비스 저장소에서 팀과 함께 고치고, 이 저장소는 측정(하루 요약, k6 시나리오)과 기록을
  맡는다.
- **목표는 API 하나가 아니라 전 범위에 하나로 정한다.** API들이 커넥션 풀과 DB를 함께 쓰므로, 한 API만 고치면 지연이 다른 API로
  옮겨 갈 수 있다. 성격이 다른 API에 예외 기준을 둘 수는 있지만, 측정하기 전에 정해 둔다.
- **원인을 확인하고, 하나씩 고친다.** 잴 때마다 목표를 가장 크게 깨는 원인 하나를 고치고, 같은 방법으로 다시 잰다. 여러 개를
  한꺼번에 고치면 무엇이 효과가 있었는지 알 수 없다. 목표를 이미 지키는 API는 손대지 않는다.
- **증상을 덮는 조치는 원인을 확인한 뒤에만 한다.** 커넥션 풀 크기를 늘리거나 서버를 키우는 일은 지연을 가릴 수는 있어도 원인을
  없애지 않는다. 원인이 정말 풀 크기나 자원일 때만 한다.
- 상시 트래픽(Locust)은 지금처럼 두고, 한계는 k6의 열린 모델(`constant-arrival-rate` 등)로 잰다. Locust는 서버가 느려지면
  요청도 덜 보내서 지연을 작게 잰다([결정 기록](2026-11-05-locust-over-k6.md)).

## 끝나는 조건 (제안값, 확정 전. 이번 범위에서는 A와 최선 기준 ①만 쓴다)

### 합격선: 서비스에 필요한 만큼

| 단계 | 조건 | 기준 | 판정 근거 |
|---|---|---|---|
| A. 지금 부하 | 8,000명 상시 트래픽, 하루 | 모든 API p95 300ms 이하, 커넥션 대기 0 (재시작 직후 5분 제외) | 하루 요약 (서버 기준) |
| B. 목표 부하 | k6 혼합 요청 **60 RPS**를 30분 유지 | 모든 API **p95 300ms, p99 800ms 이하**, 오류율 0.1% 미만, 커넥션 대기 0 | k6 (클라이언트 기준) |
| C. 여유 | k6 혼합 요청 **120 RPS**를 10분 유지 | 무너지지 않음: 오류율 1% 미만, p99 3,000ms 미만 | k6 (클라이언트 기준) |

A는 k6 환경이 정해지기 전에도 하루 요약으로 확인할 수 있다. 1단계(결함 해결)가 끝났는지를 A로 먼저 본다.

### 최선 기준: 서버가 낼 수 있는 만큼

| 기준 | 내용 |
|---|---|
| ① 유휴 성능 유지 | 60 RPS에서 각 API의 p95가 **자기 유휴 p95의 2배 이내**다. 단, 유휴 p95가 25ms보다 작은 API는 50ms까지 허용한다. 유휴 p95는 k6로 1 RPS를 줄 때의 값이다 |
| ② 한계의 원인이 자원 | 요청 속도를 계단식으로 올려 p95 300ms가 처음 깨지는 RPS(**한계**)를 기록한다. 그 지점에서 앱 서버 CPU나 DB 자원이 포화(80% 이상)되어 있어야 한다. 자원이 남는데 무너지면 아직 고칠 원인이 남은 것이다 |

- **합격선은 반드시 넘는다. 최선 기준까지 넘으면 작업을 마친다.**
- 최선 기준 ②를 만족하면 "남은 병목은 하드웨어이고, 더 버티려면 서버를 키워야 한다"고 말할 수 있다. 이 지점이 지금 조건에서
  할 수 있는 만큼 한 상태다. 2의 추정대로라면 한계는 초당 약 230-320건 근처가 된다(추정).
- 합격선만 넘고 멈춘다면, 남은 원인과 멈춘 이유(예: 고치는 비용에 비해 효과가 작음)를 이 기록의 후속 기록에 남긴다.
- 결과는 절대 숫자보다 배수와 원인으로 남긴다. 예: "초당 8건에서 7배 느려지던 원인 X를 없앴다. 이제 초당 N건까지 유휴 때의
  2배 안에 머문다. 한계는 초당 M건으로 20,000명 피크의 K배이고, 그 지점의 병목은 CPU다."

## 근거

| 값 | 근거 |
|---|---|
| 60 RPS | 8,000명의 1분 최대 24.6 TPS × 2.5배(20,000명) ≈ 61. 이 1분 최대는 23시 몰아 기록 세션 구간에서 나왔으므로, 20,000명에서도 페르소나 구성 비율이 지금과 같다는 가정이다. [트래픽 모양과 규모](2026-10-29-traffic-shape.md)가 따로 추정한 20,000명 피크 28-56 RPS와도 크게 다르지 않다 |
| 120 RPS (2배) | 순간 몰림과 데이터 증가에 대한 여유. 가정이다 |
| p95 300ms | ① 부하가 없을 때 가장 느린 `GET /growth/me`도 p95가 111-160ms다(새벽 01-05시). 300ms는 그 약 2배이므로 서버가 이미 낼 수 있는 범위 안이다. ② 홈 화면은 API 3개를 부른다. 사람이 흐름이 끊긴다고 느끼는 1초([Nielsen, Response Times: The 3 Important Limits](https://www.nngroup.com/articles/response-times-3-important-limits/)) 안에 화면이 떠야 한다. 셋을 차례로 부르는 최악의 경우에도 300ms × 3 = 900ms로 1초 안에 든다(네트워크와 화면 그리기 시간은 따로 확인 필요). 하루 요약의 주의 기준(`MAX_API_P95_MS`)과도 같다 |
| p99 800ms | 지금 p99가 1,000ms를 넘는 API가 있어 꼬리도 따로 묶는다. 1초 안에 들게 한다. 가정이다 |
| p99 3,000ms (C) | 거버너가 배율을 낮추는 기준과 같다 |
| 오류율 0.1% | 지금 하루 실패가 0건이므로 엄격하게 둔다. 가정이다 |
| 유휴의 2배 (최선 ①) | p95 300ms는 API마다 느슨한 정도가 다르다. `GET /daily-goals/{goalDate}`는 유휴 p95가 12ms라 300ms까지 25배 느려져도 합격선을 넘는다. 각 API를 자기 유휴 값과 비교해야 경합이 남았는지 드러난다. 50ms 하한은 아주 빠른 API가 측정 오차로 탈락하지 않게 하려는 값이다(가정) |
| 자원 포화 80% (최선 ②) | 이 정도면 자원이 한계의 원인이라고 볼 수 있다는 가정이다 |

버린 선택지:

| 선택지 | 버린 이유 |
|---|---|
| "성능 개선"으로 정의 | 필요의 근거가 20,000명이라는 가정에 많이 기댄다. 실제로는 지금 부하에서 이미 드러난 결함이고, 같은 날의 데이터만으로 설명된다 |
| 느린 API마다 목표를 따로 정함 | 공유 자원 때문에 한 API의 개선이 다른 API를 느리게 할 수 있고, 이를 판정하지 못한다 |
| 평균 응답 시간으로 판정 | 지금 문제는 꼬리(p95, p99)에 있다. 평균은 이를 가린다 |
| 합격선만 둠 | 필요한 만큼에서 멈추면 고칠 수 있는 원인이 남아도 알 수 없다. "더 할 수 있었는데 안 했다"는 반론에 답하지 못한다 |
| 서버 증설로 해결 | 느려지는 시간대에도 CPU·커넥션 풀·DB에 여유가 있었다. 자원이 원인이라고 확인된 뒤에만 검토한다 |

## 이 기록의 한계

- **단계별 비교에는 계정 수 말고도 달라진 것이 있다.** 4,000명 기준선은 주말, 8,000명은 평일이다. 그 사이에 다이어터 추가분
  3,800명과 휴면 직전 200명이 더해졌고, 식사 양을 목표 칼로리로 정하는 변경(11-09)이 들어갔고, 데이터가 며칠 더 쌓였다.
  backend 코드가 바뀌었는지는 확인하지 못했다.
- **백분위는 히스토그램 구간으로 추정한 값이다.** 300ms 부근의 구간 경계는 268ms와 358ms다. 그래서 p95 319ms(`POST /auth/login/dev`)
  처럼 기준에 가까운 값은 실제로 300ms 안일 수도 있다. 기준을 크게 넘는 값(600ms 이상)은 이 오차와 관계없이 넘은 것이다.
- **Prometheus는 1분마다 수집한다.** 1분보다 짧은 순간 몰림은 지표에서 보이지 않는다.
- **하루치 측정이다.** 같은 경향이 다른 날에도 나오는지는 하루 요약으로 계속 본다.
- **CPU 상한 추정은 대략적인 값이다.** 07시 값으로 계산했고, 요청 비용이 부하와 관계없이 일정하다고 가정했다. 저녁(17-24시)에는
  마지막 끼니 배치가 CPU를 따로 쓴다. 18시에는 JVM CPU 10.8%를 요청 28,313건으로 나누면 요청당 27ms가 되는데, 같은 시간 DB
  커밋이 201,204건으로 배치 몫이 대부분이다. 그래서 저녁의 한계는 아침보다 낮을 수 있고, k6로 잴 때 배치 시간대인지 함께 적는다.
- **발생기는 홈 화면 API 3개를 차례로 부른다**(`kkugi_load/sessions/steps.py`의 `open_home_with_goal`). 앱이 동시에 부른다면,
  같은 TPS에서도 실제 앱 쪽의 동시 요청이 더 많아 서버가 더 몰린다. 이 경우 지금의 측정은 실제보다 덜 나쁘게 나온 것이다.
- **인공 계정의 행동은 가정이다.** 시간대별 접속 확률과 세션 구성은 [페르소나 문서](../../docs/personas/)의 가정에서 나왔다. 실제
  사용자의 행동이 다르면 목표 부하(60 RPS)도 달라진다.

## 미결

- **발생기의 세션 시작 초는 결함을 고치는 동안 바꾸지 않는다(제안).** 지금 바꾸면 서버는 그대로인데 지연만 줄어 보여 문제를
  가린다. 같은 몰림을 두어야 고치기 전후를 같은 조건에서 비교할 수 있다. 0초 몰림의 현실성은 결함을 고친 뒤 따로 다룬다.
- **서비스 저장소에 제안할 수정.** 원인 나(요청 하나의 트랜잭션 수와 관리 문장 왕복)를 먼저 다루고, 다(풀 크기)는 그다음에
  본다. 구체적인 수정 방법은 팀과 정한다.
- **목표 숫자 확정.** 합격선과 최선 기준의 값은 제안값이다. 성격이 다른 API(예: `POST /workout-sessions`)에 예외 기준을 둘지도
  함께 정한다.
- **k6를 쏠 환경(보류).** 2(한계 확인)를 할 때 정한다. 운영 서버가 유일한 환경이라 운영 서버에 쏘면 실사용자 응답과 버스트
  크레딧이 깎인다. 선택지는 새벽(02-05시) 운영 서버, 운영 DB를 복사한 별도 환경이다.
- **앱이 홈 화면 API를 부르는 방식.** 동시에 부르는지 앱 코드에서 확인한다. 동시에 부른다면 k6 시나리오는 그대로 동시에 부르게
  만들고, 발생기의 조회 세션도 맞출지 정한다.
- **16,000명 증량과의 순서.** 전후 비교는 같은 계정 수에서 해야 한다([상시 트래픽을 흘리는 이유](2026-11-09-why-continuous-traffic.md)
  근거 절). 결함을 고치기 전에 증량할지 정해야 한다.
- **backend 재시작 20회의 원인.** 09:45-17:14의 근무 시간에 몰려 있어 팀의 배포로 본다(사용자 추정). 재시작 직후마다 커넥션
  대기와 CPU 100%가 생기므로, 작업 중에 배포 직후의 동작도 함께 확인한다.
- **데이터 서버의 버스트 크레딧.** `t3` 계열이지만 크레딧 설정과 잔량을 확인하지 않았다(확인 필요).
