## 한눈에 보기

- **무엇을 쟀나.** 꾸기 운영 서버에 인공 사용자 트래픽을 17.8시간 보내고, 요청량·응답 시간·서버 자원을 쟀다. 나중에
  서버나 발생기를 고친 뒤 같은 방법으로 다시 재서 이 값과 비교하려는 기록이다.
- **누가 보냈나.** 인공 계정 2,000개(다이어터 1,000, 운동 초보자 1,000) 중 1,433개가 실제로 요청을 보냈다. 운동
  초보자 703명은 이 구간에 처음 가입했다.
- **얼마나 보냈나.** HTTP 요청 16,400건, 업무 세션 2,557건이다. 평균 0.25 TPS, 가장 바쁜 18시가 0.90 TPS다.
- **결과.** 실패 0건이다. 서버 기준 응답 시간 p95는 대부분 80ms 이하이고, 가장 느린 것은 `GET /daily-summaries`
  146ms, `POST /workout-sessions` 134ms다. backend 서버 CPU는 평균 3.4%다.
- **결론.** 이 트래픽은 서버에 거의 부담을 주지 않는다. 병목을 찾으려면 트래픽을 크게 늘리거나 별도의 부하 실험이
  필요하다. 이 기록은 "평소 수준의 트래픽에서 API가 얼마나 빠른가"의 기준으로 쓴다.

## 이전 기준선과 비교

이전 기준선은 다이어터 1,000명만 있던 때(11-01 15시 → 11-02 15시)의 같은 시간대 값이다.

**계정 수가 아니라 세션 수로 비교한다.** 계정은 2배가 되었지만 이번 구간에 실행된 세션은 18시 기준 시간당 약 507건
→ 457건으로 오히려 적다. 그래서 18시 TPS도 1.016 → 0.902로 낮다. 같은 세션 수에서 요청과 DB 쓰기가 어떻게 달라졌는지를

세션 시간에는 생각 시간이 들어 있어 식사 기록이 14초쯤 걸리는 것이 정상이다. 서버 성능보다 세션이 끝까지 성공하는지를
보는 지표다. 단위는 ms다.

| 세션 | 건수 | 실패 | 평균 | 중앙값 | 최대 |
|---|---:|---:|---:|---:|---:|
| `beginner_view` | 1,029 | 0 | 142 | 140 | 441 |
| `beginner_workout` | 182 | 0 | 4,391 | 3,500 | 11,202 |
| `dieter_view` | 691 | 0 | 89 | 78 | 263 |
| `dieter_dinner` | 300 | 0 | 13,663 | 13,000 | 20,510 |
| `dieter_breakfast` | 190 | 0 | 13,967 | 14,000 | 21,542 |
| `dieter_weight` | 94 | 0 | 2,813 | 2,900 | 4,169 |
| `dieter_workout` | 45 | 0 | 4,474 | 3,600 | 15,624 |
| `dieter_snack` | 26 | 0 | 13,448 | 14,000 | 16,934 |

`beginner_view`는 `dieter_view`와 같은 요청 3개를 보내는데 약 50ms 느리다. 세션 시간은 로그인·온보딩이 끝난 뒤부터
재므로 그 요청 때문은 아니다. 원인은 확인하지 못했다(확인 필요).

시작 지연은 2,557건, 중앙값 420ms다. 최대 29.7분은 발생기를 켜기 직전 30분 안에 계획된 세션 42건을 켜자마자 늦게
실행한 것이다. 그 뒤로는 1분 평균이 60초를 넘은 적이 없고, 이 42건을 빼면 평균 약 0.5초다.

## 다시 재는 방법

새 측정에서 같은 표를 만드는 순서다. 명령은 저장소 루트에서 실행한다. 관측 서버 접속은 `ssh kkugi-obs`이고 설정은 README의
"서버 운영"에 있다.

1. **구간을 정한다.** 발생기 설정(계정 풀, 트래픽 양, 코드)이 바뀌지 않은 연속 구간을 고른다. Master 로그에서 배포와 조절
   시각을 확인한다.

   ```bash
   ssh kkugi-obs 'cd ~/kkugi-loadtest && docker compose -f deploy/docker-compose.yml logs master | grep -E "승인|조절"'
   ```

2. **Locust CSV를 내려받는다.** 이름에 Master 시작 시각이 붙는다.

   ```bash
   ssh kkugi-obs 'docker exec kkugi-loadgen-master-1 ls -t /app/stats'
   ssh kkugi-obs 'docker exec kkugi-loadgen-master-1 cat /app/stats/<이름>_stats_history.csv' > history.csv
   ```

3. **시간대별 TPS·세션/s와 API별 클라이언트 값을 뽑는다.** `--to`는 그 시각 이전의 마지막 기록까지 센다. API별 값은
   Master 시작부터 `--to`까지의 누적이다.

   ```bash
   python tools/stats_summary.py hourly history.csv --from '2026-11-02 15:23' --to '2026-11-03 09:10'
   python tools/stats_summary.py apis history.csv --to '2026-11-03 09:10'
   ```

4. **서버 기준 값을 뽑는다.** 관측 서버의 Prometheus(`localhost:9090`)에 구간 끝 시각(`time`, 유닉스 초)과 구간 길이를
   넣어 조회한다.

   ```bash
   ssh kkugi-obs 'curl -s --get localhost:9090/api/v1/query --data-urlencode time=1793664600 \
     --data-urlencode "query=histogram_quantile(0.95, sum by (le,method,uri)(increase(http_server_requests_seconds_bucket{synthetic=\"true\"}[17h47m])))"'
   ```

   | 값 | 쿼리 |
   |---|---|
   | API별 요청 수 | `sum by (method,uri)(increase(http_server_requests_seconds_count{synthetic="true"}[구간]))` |
   | API별 p50·p95·p99 | 위 예시에서 0.95를 0.5, 0.99로 바꾼다 |
   | 응답 코드별 수 | `sum by (status)(increase(http_server_requests_seconds_count{synthetic="true"}[구간]))` |
   | DB 커밋 수 | `sum(increase(mysql_global_status_commands_total{command="commit"}[구간]))` |
   | 시간별 DB TPS | `sum(rate(mysql_global_status_commands_total{command="commit"}[1h]))` (범위 조회, 1시간 간격) |
   | 커넥션 풀 대기 최대 | `max_over_time(hikaricp_connections_pending[구간])` |

5. **활동한 계정 수**가 필요하면 발생기 코드로 그 구간의 일정을 재현한다. 계정이 세션을 실행할지는 계정·날짜·시간대로
   정해지므로 다시 계산해도 같다(`kkugi_load/scheduler.py`의 `scale_draw`). Locust 기록의 세션 수와 맞는지 꼭 대조한다.

6. **서버 CPU와 버스트**는 Lightsail 지표로 본다. 명령은 README의 "서버 운영"에 있다.
