## 한눈에 보기

- **무엇을 쟀나.** 계정 4,000개(다이어터, 운동 초보자, 하루 몰아 기록형, 운동 숙련자 각 1,000)가 배율 1.0으로 꼬박 이틀 넘게
  돈 구간이다. 몰아 기록 세션이 몰리는 23시대를 처음으로 이틀 연속 쟀다.
- **얼마나 보냈나.** 하루 HTTP 요청 약 12만 건, 세션 약 15,600건, 평균 1.39 TPS다. 낮 최대는 18시 약 3.6 TPS, 23:00-23:30은
  약 17.5 TPS, 1분 최대는 26.9 TPS(11-08 23:10)다. 모두 예상치와 거의 같다.
- **결과.** HTTP 실패 1건, 놓친 세션 0건이다. 실패 1건은 `POST /workout-sessions`와 backend의 `LastMealBatch`가 DB 데드락에
  걸린 것이다. 커넥션 풀은 10개 중 최대 3개를 썼고, 버스트 여유는 99% 이상이었다.
- **새로 보인 것.** 매일 17:10쯤부터 00:05쯤까지 DB 커밋이 초당 약 60건으로 유지된다. 같은 시간 HTTP 요청은 초당 1-3건이므로
  발생기가 만든 부하가 아니다. 11-04 저녁부터 나타났다.
- **결론.** 4,000명 하루치 트래픽과 23시대 몰림은 서버가 무리 없이 받는다. 다만 서버 기준 p95가 2,000명 때보다 대체로
  1.5-3배 늘었고, 저녁 DB 부하는 회원 수와 함께 커질 수 있으므로 8,000명으로 늘리기 전에 원인을 확인하는 것이 좋다.

## 저녁 DB 부하

매일 17:10쯤 시작해 00:05쯤 끝난다. 5분 간격으로 보면 1분 커밋/s가 0과 60-66 사이를 오가며, 대부분의 시간에 60대다.

| 항목 (11-08, 10분 평균) | 15:00 | 21:00 |
|---|---:|---:|
| 인공 HTTP 요청/s | 약 0.5 | 1.01 |
| commit/s | 0.4 | 59.3 |
| select/s | 1.6 | 168.4 |
| set_option/s | 1.5 | 236.8 |
| insert/s | 0.07 | 2.1 |
| update/s | - | 0.08 |
| questions/s | - | 467.6 |

- **발생기가 만든 부하가 아니다.** 같은 시간 인공 HTTP 요청은 초당 1건 남짓이고, 발생기가 아닌 요청은 이 구간 전체에 약 100건이다.
- **11-04 저녁부터 나타났다.** 시간대 평균 커밋/s는 11-04 16시대 0.4, 17시대 60.9였고, 그 뒤로 매일 같은 시간에 나타난다. 11-03 저녁
  ([2,000명 저녁 기준선](2026-11-04-baseline-2000-evening.md))에는 18시대가 1.6이었다. 4,000명 단계는 11-04 09:05에 시작했고
  backend는 11-04 14:25-17:16에 9번 재시작했다. 그래서 회원 수 때문인지 backend의 새 작업 때문인지 가르지 못했다(확인 필요).
- **`LastMealBatch`로 추정한다.** 데드락이 난 19:32에 `LastMealBatch`가 `scheduling-1` 스레드에서 돌고 있었다. 이름(마지막 끼니
  처리)도 저녁 시간대와 맞는다. Loki에는 경고와 오류만 남아 있어서 배치가 언제 몇 번 돌았는지는 로그로 셀 수 없었다(확인 필요).
- **backend가 CPU를 쓴다.** JVM CPU(30분 평균)가 11-08 15:00에 0.3%, 21:00에 9.3%다. 앱 서버 CPU도 이 시간에 15-24%로
  오른다(서버 자원 절 참고). 같은 시간 인공 요청은 초당 1건 남짓이므로 요청 처리가 아닌 backend 안의 작업이 CPU를 쓴다.
- **커밋은 많지만 쓰기는 적다.** insert·update는 초당 2건 남짓이고 select가 대부분이다. 조회 위주의 트랜잭션을 아주 자주 여는
  작업으로 보인다.
- 기존의 자정 급증과는 다른 현상이다. 자정 급증은 몇 분 동안 1분 70/s 안팎으로 튀는 것이었다. 이 구간의 1분 최대는 75.2/s다.

## 다시 재는 방법

[1,000+1,000명 기준선](2026-11-03-baseline-2000.md)의 "다시 재는 방법"과 같다. 이 구간에서 다르게 한 점만 적는다.

- **API별 클라이언트 값과 세션 수는 구간 양 끝의 누적값 차이로 구했다.** Master 시작(11-04 09:05)이 구간 시작보다 앞서므로
  `tools/stats_summary.py apis`는 쓰지 않았다. history CSV의 11-06 23:59:21과 11-09 09:37:22 기록을 썼다. 날짜별 값은 각 날의
  자정에 가장 가까운 앞 기록을 썼다.
- 시간대별 TPS는 `python tools/stats_summary.py hourly history.csv --from '2026-11-07 00:00' --to '2026-11-09 09:38'`이다.
- Prometheus 조회는 `time=1794184620`(11-09 09:37), 구간 `[207420s]`이다.
- 저녁 DB 부하의 명령 종류는 `topk(12, rate(mysql_global_status_commands_total[10m]))`를 11-08 21:00과 15:00에 조회했다.
- 데드락은 Loki(관측 서버 `localhost:3100`)에서 `{service_name="kkugi-backend"} |~ "(?i)error|exception"`을 19:30-19:35로
  조회해 찾았다.
