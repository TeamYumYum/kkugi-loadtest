## 배경

4,000명 단계를 닷새 돌린 뒤, 사용자가 물었다. "계속 트래픽을 흘리는 이유는 데이터를 쌓고 예상치 못한 문제를 찾기 위해서다.
이 이유가 납득할 만한가, 근본적인 이유는 무엇인가." 이 기록은 그 답과, 거기서 나온 다음 방향을 남긴다.

## 결정

### 상시 트래픽의 목적

**어떤 문제는 순간 부하가 아니라 시간과 쌓인 상태에서만 드러난다. 그 문제를 실제 사용자보다 먼저 겪기 위해 트래픽을 흘린다.**

- 짧은 부하 테스트(k6)는 "초당 몇 건까지 버티는가"에 답한다. 상시 트래픽은 "며칠, 몇 주 돌면 무엇이 깨지는가"에 답한다.
- 계정 수 증량은 요청 부하보다 **회원 수에 비례하는 비용**을 시험한다. 4,000명이 평균 1.4 TPS뿐이지만, 회원 전체를 도는 backend
  작업은 계정 수만큼 커진다.
- 데이터 축적은 그 자체가 목적이라기보다 위 문제를 만드는 조건이다. 테이블이 커지고 기록이 쌓여야 드러나는 문제가 있다.

지금까지 상시 트래픽으로 찾은 문제가 근거다. 모두 짧은 부하 테스트로는 찾지 못했을 것이다.

| 찾은 문제 | 드러난 조건 |
|---|---|
| 17-24시 DB 커밋 약 60/s (마지막 끼니 배치가 매분 회원 전체를 순회) | 저녁 시간, 회원 수 |
| `POST /workout-sessions`와 그 배치의 데드락 | 배치가 도는 시간의 쓰기 |
| `GET /growth/me` 응답 1,360B → 2,261B | 며칠간 기록 축적 |
| 배포 때의 502가 거버너를 움직임 (11-04) | 운영 중 배포 |
| GC 정지 합계가 트래픽보다 빠르게 늘어남 | 장시간 실행 |
| 섭취 칼로리가 목표와 무관했던 데이터 | 쌓인 데이터를 들여다봄 |

### 방향 (사용자 결정)

- **양보다 현실성(품질)이 중요하다.** 비현실적인 데이터는 오래 쌓아도 기능을 시험하지 못한다. 데이터 품질 점검과 페르소나 개선을
  **정기적으로** 한다.
- **페르소나가 쓰지 않는 기능을 어떻게 시험할지는 고민 중이다.** 사진 인식, 마지막 끼니 추천 새로고침, 식사 삭제, 탈퇴가 해당한다.
  사진 인식은 AI 서버 비용이 든다.
- **문제를 자동으로 잡는 장치를 만든다.** 저녁 DB 부하는 11-04부터 있었지만 11-09에 손으로 뒤져서야 찾았다. 하루 요약 보고서와
  경보를 둔다.
- **단계마다 확인할 질문을 먼저 정한다.** 늘려 보고 무엇이 보이는지 지켜보는 대신, 판정할 수 있는 질문을 둔다.

## 근거

- 8,000명 단계에서 Worker가 8개에서 12개로 늘어나는 것은 관측 서버에 부담이 되지 않는다. 11-09 11:40의 `docker stats`에서
  Worker 하나가 CPU 0.1-1.2%, 메모리 40-53MB였고, 서버의 사용 가능한 메모리는 약 1.3GB였다. 그래서
  [계정 번호 구간](2026-11-02-account-ranges-and-ramp.md) 결과 절의 "Worker 구성 두 안"은 고르지 않고 지금 구조를 유지한다.
- 성능 개선 전후 비교와 증량은 서로 충돌한다. 사용자는 증량을 먼저 고르면서 머지를 하루 미뤘다. backend 성능 개선을 측정할
  때는 그 시점의 계정 수로 전후를 잰다.

## 결과

### 8,000명 단계에서 확인할 질문

- 저녁 배치의 DB 커밋이 회원 수에 비례해 약 2배(약 120/s)가 되는가. 그때 저녁 p95와 데드락 빈도는 어떻게 되는가.
- 자정 하루 목표 판정과 월요일 주간 리포트 생성 시간이 회원 수에 비례해 늘어나는가.
- 새 계정 4,000개가 처음 세션에서 로그인·온보딩할 때 `[auth]`, `[setup]` 요청이 실패 없이 지나가는가.
- 다이어터 추가분이 기존 다이어터와 같은 달성률 분포를 보이는가.
- 휴면 직전 계정의 드문 접속에서 토큰 재발급 실패 같은 문제가 생기는가.

## 미결

- 페르소나가 쓰지 않는 기능을 시험할 방법.
- 경보를 보낼 곳. 관측 서버의 Grafana에는 경보 설정이 아직 없다.
- 데이터 품질 점검의 주기와 항목.
- 워치 유저를 뺀 최종 비율(이전 기록에서 이어짐).
