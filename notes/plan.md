# 구현 계획

마지막 갱신: 2026-10-29. 트래픽 숫자와 근거는 [트래픽 모양과 규모](decisions/2026-10-29-traffic-shape.md)를 본다.

작업 하나를 끝낼 때마다 커밋한다.

## 단계 1. 트래픽 모양

방식은 [시간대별 표](decisions/2026-10-29-hourly-table.md)를 따른다.

- [ ] 시간대별 표 설정: 칸마다 계정 하나가 앱을 열 확률을 둔다. 시간대별 기대 세션 수(계정 수 × 표 값)를 계산하는 테스트를 둔다
- [ ] 계정별 활동 성향: 계정마다 고정 배수(평균 1)를 곱한다
- [ ] 조회 세션: 앱을 열어 홈 화면만 본다(요약, 목표, 성장)
- [ ] 일정 생성을 표 기반으로 바꾼다: 피크 시간대는 주로 식사 기록, 일반 시간대는 주로 조회. 다이어터의 식사 창을 이 방식으로 바꾼다
- [ ] 활성 계정 상한: `base` 풀 범위를 크게 잡고 상한(10,000 → 20,000)까지만 일정을 만든다. 새 계정은 첫 세션에서 로그인·온보딩한다
- [ ] `peak-*` 풀 번호 옮기기: 지금 `peak-1`이 10,000번부터라 `base`를 20,000개로 넓히면 겹친다. 예: 100,000번 이후로 옮긴다

## 단계 1.5. 실행 중 설정 바꾸기 (제안, 미결)

- [ ] Master가 설정 파일을 다시 읽어 Worker들에게 표·배율을 보내고, Worker는 지금 이후 일정을 다시 만든다. 노트북 Worker도 같은 값을 받는다
- [ ] Locust 웹 UI에 다시 읽기, 배율, 정지 조작을 더한다
- [ ] 실행기 수 배분: Locust는 Master의 User 수를 Worker에 고르게 나눈다. Worker마다 필요한 실행기 수가 달라 해결 방식을 정한다

## 단계 2. 운영 안전장치

- [ ] 전역 배율과 정지 스위치: 계획된 세션을 배율 확률로만 실행한다. 계정·날짜로 결정해 재시작해도 같은 세션이 골라지게 한다
- [ ] 거버너: Master가 최근 실패율과 p99를 보고 배율을 낮추고 Worker에 알린다
- [ ] Master `/metrics`: 세션 결과, 놓친 세션, 시작 지연, 배율, Worker별 계정 수. 응답 시간 히스토그램을 만드는 방식은 구현할 때 비교한다

## 단계 3. 배포

- [ ] 요청 경로 분할: 세션 단위로 프라이빗 95%, 공인 5%. 경로별로 통계를 나눈다
- [ ] Dockerfile과 compose: Master와 상시 Worker, 자원 상한, 상태 DB 볼륨, 도메인과 프라이빗 IP 매핑. 웹 UI는 외부에 열지 않는다
- [ ] 구분 헤더 값 반영: backend 작업이 끝나면 `[synthetic]`에 넣는다

## 단계 4. 운영

근거는 [시작 규모와 관측 서버 부담](decisions/2026-10-29-start-scale-and-load.md)을 본다.

- [ ] 계정 1,000개로 실측한다: 요청 1건당 발생기 CPU, 요청 1건당 Loki·Tempo 증가량, 관측 서버 CPU 크레딧
- [ ] 실측값으로 10,000개를 계산해 버틸 수 있으면 올린다
- [ ] 같은 방식으로 20,000개를 판단한다
