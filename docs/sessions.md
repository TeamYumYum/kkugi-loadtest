# 페르소나와 세션

발생기가 계정마다 어떤 API 흐름을 실행하는지 정리한다. 페르소나나 세션을 더하거나 바꾸면 이 문서도 함께 고친다.
숫자 설정값은 `config/default.toml`이 기준이다.

- **페르소나:** 계정의 성격이다. 계정 프로필을 만들고, 앱을 연 시각마다 어떤 세션을 실행할지 고른다. `kkugi_load/personas/`
- **세션:** 앱을 한 번 열어서 하는 일이다. 요청 순서와 결과 검증을 담는다. 여러 페르소나가 같은 세션을 함께 쓴다. `kkugi_load/sessions/`

## 페르소나 목록

| 페르소나 | 상태 | 쓰는 세션 |
|---|---|---|
| 다이어터 `dieter` | 구현. 지금은 모든 계정이 다이어터다 | 식사 기록, 조회 |

다른 페르소나는 계정 1,000개 실측 뒤에 하나씩 더한다([결정 기록](../notes/decisions/2026-10-29-persona-scope.md)).

## 모든 세션에 공통인 것

### 앱을 여는 시각

모든 페르소나가 공통 시간대 표로 정한다. 계정은 시간대마다 최대 한 번 앱을 연다. 규칙은 [README 실행 모델](../README.md#실행-모델).

### 세션 전 준비

세션마다 먼저 실행한다(`sessions/steps.py`의 `ensure_ready`). 이미 준비된 계정이면 요청을 보내지 않는다.

| 순서 | API | 언제 |
|---|---|---|
| 1 | `POST /auth/login/dev` | 토큰이 없을 때 |
| 1 | `POST /auth/refresh` | 액세스 토큰 만료가 120초 안으로 남았을 때. 거절되면 다시 로그인한다 |
| 2 | `POST /members/me/onboarding` | 온보딩 전일 때. 409 `MEMBER_ALREADY_ONBOARDED`는 정상으로 본다 |

통계에서는 이름 앞에 `[auth]`, `[setup]`이 붙는다. 계정마다 처음 한 번 몰리므로, 새 계정을 띄운 직후에 많이 보인다.

### 탈퇴된 계정

어느 요청에서든 401 `MEMBER_WITHDRAWN`을 받으면 그 세션을 끝내고 `ACCOUNT withdrawn`으로 센다. 실패로 세지 않는다.
계정의 generation을 올리므로 다음 세션은 새 이메일로 가입부터 다시 한다.

## 다이어터 `dieter`

식단 관리를 하는 사용자다. 끼니 때 앱을 열면 그 끼니를 기록하고, 그 밖에는 홈 화면만 본다(`personas/dieter.py`).

**프로필.** 계정 번호로 정해지고 바뀌지 않는다.

- 목표 `LOSE`, BMI 23-29의 키와 몸무게, 활동량은 `SEDENTARY`·`LIGHT`·`MODERATE` 중 하나다.
- 점심·저녁 검색어로 쓸 선호 음식 4개를 `main_keywords`에서 고른다.

**세션 고르기.** 앱을 연 시각마다 아래 규칙으로 고른다.

| 연 시각 | 실행하는 세션 | 통계 이름 |
|---|---|---|
| 아침 창(06-09시)에서 그날 처음 | 60% 확률로 식사 기록, 아니면 조회 | `dieter_breakfast` |
| 점심 창(11-14시)에서 그날 처음 | 95% 확률로 식사 기록, 아니면 조회 | `dieter_lunch` |
| 저녁 창(17-20시)에서 그날 처음 | 90% 확률로 식사 기록, 아니면 조회 | `dieter_dinner` |
| 그 밖의 모든 경우 | 조회 | `dieter_view` |

그래서 끼니마다 식사 기록은 하루 최대 한 번이다. 끼니 창과 확률은 `[personas.dieter.meals.*]`에 있다.

## 세션

### 식사 기록 `meal_log`

앱을 열고, 음식을 검색해 한 끼를 저장하고, 바뀐 요약을 확인한다(`sessions/meal_log.py`). 한 세션이 약 14초 걸린다.

| 순서 | API | 하는 일 |
|---|---|---|
| 1 | `GET /daily-summaries/{date}` | 홈 화면. 오늘 요약 |
| 2 | `GET /daily-goals/{date}` | 홈 화면. 오늘 목표. 404는 코칭 계획이 없는 것이라 정상으로 본다 |
| 3 | `GET /growth/me` | 홈 화면. 성장 기록 |
| 4 | `GET /meals?date=...` | 오늘 식사 목록. 이 끼니를 이미 기록했으면 여기서 끝내고 `(skipped)`로 센다 |
| 5 | `GET /foods?keyword=...` | 음식 검색. 음식마다 한 번, 한 끼에 2개 |
| 6 | `POST /meals` | 검색 결과에서 고른 음식과 양(100-300g)으로 저장. 201, 같은 내용을 다시 보낸 경우 200 |
| 7 | `GET /daily-summaries/{date}` | 저장 뒤 요약 |

- 1-4는 앱이 자동으로 부르는 조회라 사이에 기다리지 않는다.
- 검색 전에 2-6초(검색어 입력), 결과에서 고르기 전에 1-4초(음식 선택)를 기다린다. `[think_time]`
- 아침은 `breakfast_keywords`에서, 점심·저녁은 계정의 선호 음식에서 검색어를 뽑는다. 결과가 비면 남은 후보로 다시 검색한다.

**검증.** 아래가 맞지 않으면 실패로 센다.

- 저장 응답의 `clientUuid`, `mealType`, 먹은 날짜, 음식 ID와 양이 보낸 값과 같다.
- 저장 뒤 요약의 섭취 칼로리가 저장 전보다 저장한 식사 칼로리만큼(오차 1kcal) 늘었다.

`clientUuid`는 이메일, 날짜, 끼니로 정해진다. 그래서 세션을 다시 실행해도 같은 끼니가 두 번 저장되지 않는다.

### 조회 `view`

홈 화면만 보고 닫는다(`sessions/view.py`).

| 순서 | API | 하는 일 |
|---|---|---|
| 1 | `GET /daily-summaries/{date}` | 오늘 요약 |
| 2 | `GET /daily-goals/{date}` | 오늘 목표. 404는 정상으로 본다 |
| 3 | `GET /growth/me` | 성장 기록 |

**검증.** 요약의 날짜가 요청한 날짜와 같아야 한다.
