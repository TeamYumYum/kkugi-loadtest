## 1. 이력서에 바로 쓸 수 있는 문장

> **꾸기(식단·운동 기록 앱) 상시 인공 트래픽 발생기와 성능 진단** · Python, Locust, Docker Compose, Prometheus·Grafana·Tempo·Loki, AWS Lightsail · 2026.10–11

- 페르소나 5종(다이어터, 운동 초보자, 하루 몰아 기록형, 운동 숙련자, 휴면 직전)의 하루를 재현하는 **Locust 기반 상시 트래픽 발생기**를 설계·구현하고 운영 서버에 배포했다. 계정 수를 1,000 → 2,000 → 4,000 → 8,000으로 2배씩 늘리며 단계마다 기준선을 측정했다(8,000명 단계: 하루 요청 약 22만 건, 실패 0).
- 상시 트래픽으로 **짧은 부하 테스트로는 드러나지 않는 결함**을 찾았다. 매분 회원 전체를 순회하는 배치(저녁 DB 커밋 초당 약 60건), 배포 때의 502가 자동 감속 장치를 오작동시키는 문제, 초당 7~8건에서 홈 화면 API가 유휴 대비 7~24배 느려지는 커넥션 경합이 그 예다.
- `GET /growth/me` 지연을 Tempo 추적으로 분해해 **요청 하나가 DB 커넥션을 7번 빌리고 DB와 37번 왕복하며, 그중 26번이 트랜잭션 관리 문장**임을 밝혔다. 대기열 계산(50건 ÷ 풀 10 × 95ms ≈ 475ms)이 관측 최대값(474~501ms)과 맞는 것으로 원인을 확정하고, 트랜잭션을 하나로 묶는 수정(커넥션 획득 6회 → 1회, 테스트 기준)을 서비스 저장소에 병합했다.
- 경보를 "지금 사람이 움직여야 하는 것"만 남기도록 재설계하고, Grafana 경보 8개를 **git 파일 하나와 API 도구(diff/apply/export)로 관리**하게 바꿨다. 재시작 없이 반영되고, 빈 Grafana에서도 명령 하나로 재현된다.
- **Claude Code를 팀원처럼 운용했다.** 설계 에이전트 → 구현 에이전트 → 서비스 저장소 에이전트로 인계 문서를 넘기는 사슬을 만들고, 서브에이전트 19개에 파일 소유권·git 금지·테스트 기준선을 명시한 지시서를 주어 병렬로 구현시켰다. 결과는 매번 다시 돌려 검증했고(테스트 23 → 366건, 건너뜀 0 유지), AI가 틀린 장면에서 나온 교정은 메모리·스킬·결정 기록으로 굳혀 다음 세션에 자동으로 적용되게 했다.

## 2. 프로젝트 개요

### 2.1 무엇을, 왜

꾸기는 실사용자가 거의 없는 팀 프로젝트다. 그래서 인공 계정 수천 개가 **며칠, 몇 주 동안 현실적인 하루를 보내며** 운영 서버에 요청을 보내고 데이터를 쌓게 했다. 목적은 결정 기록(`notes/decisions/2026-11-09-why-continuous-traffic.md`)에 이렇게 정리되어 있다.

> 어떤 문제는 순간 부하가 아니라 시간과 쌓인 상태에서만 드러난다. 그 문제를 실제 사용자보다 먼저 겪기 위해 트래픽을 흘린다.

짧은 부하 테스트(k6)는 "초당 몇 건까지 버티는가"에 답하고, 상시 트래픽은 "며칠 돌면 무엇이 깨지는가"에 답한다. 두 역할을 나눈 근거는 `notes/decisions/2026-11-05-locust-over-k6.md`에 있다. 이 기록은 "k6로는 안 된다"가 아니라 "우리 요구사항을 채우는 비용이 Locust에서 더 낮았다"는 논지로 썼다.

## 3. 문제 해결 사례

각 사례는 "상황 → 과정 → 판단 → 결과"와 **내가 한 역할**로 정리했다. 포트폴리오에는 3.1을 대표 사례로 쓰는 것을 권한다.

### 3.1 대표 사례: 초당 7~8건에서 홈 화면 API가 몇 배씩 느려진다 (`GET /growth/me`)

**상황.** 8,000명 단계가 처음 하루를 채운 11-10, 하루 요약에 "p95 300ms 초과 API 8개"가 떴다. `GET /growth/me` p50은 새벽 52ms에서 18시 380ms가 되었는데, 그때 JVM CPU는 평균 10.8%였고 DB도 여유가 있었다.

**같은 신호가 6일에 걸쳐 세 번 나타났다.** 대화 기록을 이어 보면 이 문제는 한 번에 발견된 것이 아니다.

| 날짜 | 무엇을 봤나 | 그때의 판단 |
|---|---|---|
| 11-05 | 하루 통계에서 `GET /growth/me` p95가 123ms → 311ms로 회귀. 느린 요청의 시간 구성은 커넥션 대여 39%, 설정 왕복 32%, 쿼리 19% | 원인 후보로 기록. 사용자는 "아직 해결하지 않았다"며 포트폴리오 정리에서 뺐다 |
| 11-05 | 커넥션 풀 포화를 대시보드로 직접 보려다, 느린 1% 요청 229건 중 228건이 **매분 0~3초에 시작**한 것을 발견 | Claude가 "인공 트래픽 생성기가 만든 패턴이라 서버를 고칠 대상이 아니다"로 분류 |
| 11-11 | 같은 몰림을 Tempo 추적으로 다시 확인. Claude가 "결함의 상당 부분은 발생기가 만든 것"이라며 발생기 수정을 먼저 권함 | **사용자가 뒤집음**: "1초내에 같은 api가 40-50건이 들어오면 느려지는게 당연한거야? 그게 아니라면 발생기의 문제가 아니라 서버의 문제라고 생각하는데." |

세 번째 판단 전환이 이 사례의 핵심이다. 1초에 50건은 합격선(초당 60건)보다 작은 부하이고, 알림을 한꺼번에 보내면 실사용자도 같은 순간에 몰린다. 그래서 몰림은 **원인이 아니라 약점을 드러낸 조건**으로 정리했고, 고치는 동안 발생기는 바꾸지 않기로 했다(전후 비교를 지키기 위해서다).

**원인을 좁힌 과정.**

1. 재시작이 원인인지 먼저 배제했다. 재시작이 없던 시간대만 따로 집계해도 기준을 넘었다.
2. Hikari 누적 지표를 봤다. 07시 한 시간 동안 커넥션을 쓴 시간의 합은 775초인데, **기다린 시간의 합은 1,722초**였다. 1분 간격 표본이 짧은 몰림을 놓치고 있었다.
3. Tempo 추적 152건을 받아 보니 모두 매분 0~1초에 도착했다. 느린 요청 한 건(474ms)은 커넥션 대기가 348ms(73%), 실제 쿼리는 41ms였다.
4. 사용자가 다이어그램을 세 번 반려하면서(6절 5항) 그림이 분석 도구가 됐다. 반려 사유는 "내용이 너무 압축된거 같은데..? 더 길어져도 되니까 화살표랑 시퀀스를 더 추가해도 돼"와 "트랜잭션 없음" 표기의 오류였다. 화살표를 하나씩 그리자 **요청 하나가 커넥션을 7번 빌리고, DB 왕복 37번 중 26번이 트랜잭션 관리 문장(SET, COMMIT)**이라는 사실이 드러났다.
5. 사용자의 질문마다 계산으로 확인했다.
   - "84ms인데 기다리는 이유가 뭐지?" → 50건 × 84ms ÷ 풀 10 ≈ 420ms, 아침 실측 최대 553ms와 맞음. 저녁에는 매분 0초에 같이 도는 배치가 겹쳐 982ms까지 늘어남
   - "8번이나 잡으려고 시도한것도 문제 아냐?" → 시뮬레이션에서 같은 점유 시간이라도 7번 나눠 빌리면 평균 응답이 252ms → 396ms(1.6배)
   - "의도적으로 트랜잭션을 나눈 이유가 뭘까?" → 코드 이력을 추적해, 이전 리뷰에서 "요청 하나가 커넥션 3개를 쥐어 풀 고갈" 결함을 피하려고 잘게 쪼갠 부작용임을 확인
   - 리틀의 법칙(평균 동시 사용 = 도착률 × 점유 시간)으로 평균 사용 커넥션 0.22개(측정 0.2)를 맞춰, 문제가 평균이 아니라 순간 몰림이라는 것을 교차 확인

**판단.** 문제를 "성능 개선"에서 "느리면 안 되는데 느려지는 결함 해결"로 다시 정의했다(사용자의 요약 문장에서 나왔다). 범위는 결함 해결 하나로 좁히고, k6 한계 측정과 성능 개선은 보류했다. 고치는 순서는 사용자가 Growth 도메인 담당자와 대화 밖에서 합의해 정했다: 1단계로 트랜잭션을 묶고, 2단계로 조회 요청에 섞인 쓰기(뱃지 지급)를 분리한다.

**결과.**
- 서비스 저장소의 엄격 판정 절차(플랜 승인 → 구현 → 독립 리뷰 두 세션 → 합집합 대조표 → MR)로 수정했다. 줄 뱃지가 없는 요청(관측 40건 중 39건)은 읽기 전용 트랜잭션 하나로 처리한다.
- 테스트 기준 커넥션 획득 6회 → 1회. 예전 코드로 되돌리면 새 테스트가 실패하는 것까지 확인했다(변이 검증). 전체 빌드 1,984건 실패 0(건너뜀 7은 MySQL·AI 환경 의존으로 이름까지 확인).
- 독립 리뷰 두 세션의 발견 5건을 모두 반영했고, 그중 4건은 두 리뷰가 따로 같은 것을 짚었다.
- MR !505는 11-11 17:57에 병합됐다.
- **운영 효과는 아직 측정하지 않았다.** 11-12의 `GET /growth/me` p95는 412ms(11-10은 632.8ms)지만, 그 기록 스스로 "배포 시각을 확인하지 않았으므로 이 표로 효과를 판정하지 않는다"고 적었다. 포트폴리오에 개선 수치를 쓰려면 먼저 이 측정이 필요하다.

**내가 한 역할.** 원인 판단을 첫 원리로 반박해 방향을 바꿨고, 문제를 다시 정의했고, 팀 합의로 수정 순서와 담당을 정했고, 판단 과정을 문서로 남기게 했다(결정 기록의 "판단과 결정의 과정" 표 12단계). 코드 구조 결함(Reader가 Service를 거꾸로 부름)도 MR을 올린 뒤 직접 검토해 잡았다.

### 3.2 저녁마다 DB 커밋이 초당 60건 유지된다

- **상황.** 주말 기준선을 정리하다 매일 17:10~00:05 동안 DB 커밋이 초당 약 60건인 것을 발견했다. 같은 시간 HTTP 요청은 초당 1~3건이었다.
- **과정.** Locust 기록 → Prometheus → Lightsail 지표 → Loki(19:32의 500이 마지막 끼니 배치와의 데드락) → DB의 `shedlock` 테이블(작업이 1분마다 잠금을 잡음) → 서비스 코드 순으로 좁혀 `LastMealScheduler`가 17시~자정 매분 열린 계획 전체를 순회하는 것을 확인했다.
- **판단.** 부하가 이미 11-04부터 있었는데 11-09에 손으로 뒤져서야 찾았다. 그래서 "문제를 자동으로 잡는 장치"(하루 요약, 경보)를 바로 만들기로 했다(사용자 결정).
- **검증.** Locust가 보낸 쓰기와 DB 행을 날짜별로 맞췄다(11-07 식사 6,613 / 6,613, 운동 1,708 / 1,708).

### 3.3 Locust p95는 1초를 넘는데 backend 대시보드에는 안 보인다

- **상황.** 사용자: "locust 상으로 p95가 1000ms이상 인게 있는데. 실제로 꾸기 backend에 보이는 지표에 응답시간 p95가 1000ms이상 올라가는게 안보이는데"
- **원인.** 시작 직후 1분에 실행기 422개가 한꺼번에 로그인했다. Locust 표는 누적값이라 그 1분이 계속 남고, 대시보드 p95는 모든 API를 합쳐 계산해 느린 API가 희석됐다. 그 뒤 5,566건의 1분 평균 최악값은 260ms였다.
- **이어진 개선(MR !394).** API별 p95 패널, 느린 요청 표, exemplar(그래프의 한 점에서 그 순간의 추적으로 바로 가는 기능)를 넣었다. 켬·끔 성능 비교(각 1,500건)로 영향이 오차 범위 안임을 확인했다.
- **과설계를 깎은 장면(MR !398).** 팀원 MR은 DataSource 래퍼로 모든 커넥션 대여를 기록했다. Claude의 첫 제안은 래퍼 개선이었는데, 사용자가 물었다. "오히려 다른 지표를 통해 유추가능한데 불필요하게 만드는건 아닌가? 아님 간접적으로 확인할 수 있는 방법이 있는데 어려운 구현으로 가는것이 아닌가?" 실제 추적을 열어 보니 MySQL 드라이버와 OTel Agent가 이미 필요한 구간을 내보내고 있었다. 래퍼와 테스트 15건을 지우고 설정 한 줄만 남겨 **backend 실행 코드 증가가 0줄**이 되었다.

### 3.4 인공 계정의 운영 로그인: backend 코드를 바꾸지 않고 해결

- Claude는 "전용 도메인이 없으면 인공 회원을 구분할 수 없다"며 비밀값 헤더로 보호하는 새 로그인 경로를 권했다.
- 사용자가 다음 날 세 번 되물었다. "개발용 로그인으로는 왜 안된다고 했지? 단순히 서버에 켜지 않아서가 아니잖아", "어차피 사이드 프로젝트라서 이메일만으로 인증이 끝나도 상관없긴함", "코드가 그렇게 되어 있어?"
- Claude가 코드를 다시 확인하고 판단이 틀렸다고 인정했다. 기존 개발용 로그인을 켜고 예약 도메인 이메일 패턴(`lt-<번호>@synthetic.kkugi.test`)으로 구분하는 안으로 바뀌었다. 이 과정에서 "이메일 구분은 DB까지만 된다"는 빈틈도 드러나, 지표에는 값 두 개짜리 태그(`synthetic=true/false`)만 더하게 했다. 헤더 값을 그대로 태그에 넣으면 시계열이 무한히 늘어나기 때문이다.

### 3.5 배포 때의 502가 자동 감속 장치를 움직인다

- 점심 피크에 배율이 1.0에서 0.5로 떨어져 세션 510개가 건너뛰어졌다.
- 실패 68건이 모두 nginx 502였고, `process_start_time_seconds`의 변화 시각(이틀간 재시작 18회)과 겹쳤다. Lightsail CPU 최대치도 트래픽 피크가 아니라 재시작 시각이었다.
- 거버너 코드를 읽어 "5분 창 요청이 200건 미만이면 판단하지 않는다" 때문에 한가한 시간에는 배율이 다시 오르지 않는 구조라는 것도 밝혔다.
- 이 사례는 "상시 트래픽으로 찾은 문제" 목록에 근거로 들어갔다.

### 3.6 데이터 품질: 하루 목표 달성률 약 10%

- **상황.** 아침 한 끼 평균 1,042kcal, 간식 1,130kcal로 점심보다 무거웠다. 음식 양을 칼로리와 무관하게 100~300g에서 뽑았기 때문이다. 하루 목표 달성률은 약 10%였고 "식단 7일" 배지를 받은 계정은 0명이었다.
- **교정.** Claude가 사용자 제안을 "성공 70% / 실패 30%"로 정리해 질문하자 사용자가 반려했다. "30%의 사용자는 계속 실패하는 걸로 뜨잖아. 내 말은 90%이상 확률로 성공하는 무리 절반, 60%이상 확률로 성공하는 무리 절반으로 다이어터 그룹을 나누자는거였어." "삼시세끼가 목표가 아니라" 기록한 칼로리만 보게 했다.
- **결과.** 예상 달성률은 페르소나별 67~72%다. 이전 코드를 꺼내 새 코드와 일정 7,957건을 대조해, 요청 수와 순서가 그대로라는 것(기준선 비교가 깨지지 않는다는 것)을 증명했다. 실제 달성률 확인은 남은 일이다.

### 3.7 경보: 소음을 줄이고 git으로 관리한다

- 사용자 원칙: "중요한 정보만 alert되는게 맞잖아. 불필요하게 쓸모없거나 과한 정보는 빼는게 좋지 않을까?" DB 커밋 급증(용량 지표), backend 재시작(배포마다 울림), 발생기 HTTP 실패(5xx 경보와 중복)를 빼고 하루 요약의 "주의"로 옮겼다.
- "10분 전보다 10배" 경보는 넣지 않았다. 발생기가 06시와 23시에 매일 40~60배 급증을 만들기 때문이다. 대신 "발생기가 아닌 트래픽 급증"을 넣었다.
- Claude가 처음에 서비스 저장소를 피하려고 커스텀 감시 컨테이너를 만들자, 사용자가 "그냥 지금 grafana 경보를 쓰면 안됨?"이라고 해서 Grafana 내장 경보로 옮겼다.
- 팀원의 파일 방식 경보와 충돌하자 `deploy/grafana/alerting.yaml`을 기준으로 삼고 `tools/grafana_alerts.py`(diff, apply, export)로 관리하게 했다. 사용자의 "그래서 재현 가능하다는거지?" 질문 뒤 실제 서버에서 `diff` 종료 코드 0을 확인했다.
- 경보와 하루 요약은 8,000명 첫 저녁의 이상(거버너 감속, 커넥션 대기 최대 70)을 사람보다 먼저 잡았다. 이것이 3.1의 출발점이 됐다.

### 3.8 AI의 틀린 설명을 실험으로 정정하고, 조용히 줄어드는 구조를 막는다

- Claude는 "새로 붙은 Worker에는 실행기를 다시 나누지 않는다"고 설명했고 README에도 그렇게 적혀 있었다.
- 사용자가 "그럼 테스트를 해보자"라고 해서 로컬에서 Worker를 붙였다 떼 봤다. 결과는 반대였다. 붙을 때는 기본 설정에서도 다시 나누고, **떨어질 때 실행기가 사라진 채 남는 것**이 진짜 문제였다.
- `--enable-rebalancing` 옵션 없이 Master가 뜨면 경고 대신 **시작하지 않도록** 했다. "옵션을 빠뜨리면 실행기가 조용히 줄어드는 구조"이기 때문이다. 전역 지침의 "검사 장치가 조용히 꺼지는 구조를 만들지 않는다"가 코드로 옮겨진 사례다.

## 4. AI 활용 방식 (핵심)

### 4.1 한눈에 보는 역할 분담

| 사람(나)이 한 일 | AI(Claude)에게 맡긴 일 |
|---|---|
| 목적과 범위 정하기, 문제 재정의 | 서버·코드·지표 조사, 측정, 계산 |
| AI 결론을 질문으로 검증하기 | 구현(직접 또는 서브에이전트), 테스트 |
| 팀원과의 합의(대화 밖에서) | 결정 기록·용어집·PR 본문 작성 |
| 머지·배포·운영 변경의 최종 승인 | 승인된 범위 안의 배포와 사후 확인 |
| 피드백을 규칙으로 정하기 | 그 규칙을 메모리·스킬·지시서에 반영 |
| 비용 판단(언제 검증을 멈출지) | "확인 필요"와 남은 위험 보고 |

### 4.2 여러 에이전트를 사슬로 운영했다

이 저장소 자체가 다른 에이전트의 인계 문서로 시작했다.

```text
서비스 저장소 설계 세션(10-28)          SSH로 서버 실측, 운영 문서·ADR 작성
        │  인계 문서 locust-traffic-generator-handoff.md
        ▼
이 저장소 구현 세션(10-28~)              발생기 구현, 서브에이전트 19개 지휘
        │  인계 문서 synthetic-traffic-backend-handoff.md
        ▼
서비스 저장소 에이전트                   개발용 로그인 활성화, synthetic 태그
        │  완료 보고를 사용자가 붙여 넣음 → Claude가 코드로 재확인
        ▼
서비스 저장소 작업(11-04~, 11-11)        Codex 구현(Orca CLI) + 독립 리뷰 세션 R1·R2
```

- 인계 문서와 위임 지시서는 **저장소 루트에 untracked로** 두고 사용자가 직접 옮겨 다른 세션에 투입한다(메모리 `delegation-docs-untracked`). 저장소 기록(`notes/`)과 위임 문서를 섞지 않는 규칙이다.
- 인계 문서에는 확정 사항과 제안값을 표로 나누고 "존재하지 않는 API 필드를 추측해 구현하지 않는다", "장시간 실험은 실제로 완료한 경우에만 완료했다고 보고한다" 같은 금지 문장을 넣었다.
- 다른 세션의 완료 보고를 붙여 넣어도 Claude가 그대로 믿지 않고 코드에서 다시 확인했다(예: `MEMBER_WITHDRAWN` 응답이 실제로 있는지).
- 팀원용 프롬프트(SSH 터널 안내)도 Claude에게 쓰게 했다. AI를 "다른 사람의 AI에게 줄 지시서를 만드는 도구"로도 썼다.

### 4.3 질문으로 AI의 결론을 검증했다

대화 기록에서 가장 많이 반복되는 패턴이다. 사용자는 이해를 위해 물었지만 결과적으로 검토자 역할을 했고, AI의 틀린 판단 상당수가 이 질문에서 드러났다.

| 질문 유형 | 대표 발언 | 결과 |
|---|---|---|
| "당연한가?"로 원인과 조건 가르기 | "1초내에 같은 api가 40-50건이 들어오면 느려지는게 당연한거야?" | 발생기 수정 권장 철회, 서버 결함으로 재정의(3.1) |
| 근거 위치 요구 | "코드가 그렇게 되어 있어?" | 이메일 구분이 DB까지만 된다는 빈틈 발견(3.4) |
| 앞뒤 모순 지적 | "저번에는 모니터링 대시보드에 문제가 생길수도 있다고 했는데" | Claude가 "실행기 수만 계산한 이야기였다, 아직 측정하지 않았다"고 정정 |
| 실험 요구 | "그럼 테스트를 해보자. rebalance-enableing도 테스트 해보고" | README의 틀린 설명 정정(3.8) |
| 계산식 요구 | "너는 아까 어떤 기준으로 산정했는데?" | Claude가 TPS를 세션 수로 셌다는 것을 밝힘 → TPS, 세션/s, DB TPS 세 용어 정의 |
| 숨은 전제 깨기 | "완전 새로운 계정아니야? 혹시 1000명 내에서 페르소나를 나누려고 하는건가?" | 기존 계정을 나누던 설계를 새 번호 구간 방식으로 전환 |
| 자기 말로 요약 | "그러면 성능의 개선이 아니라 느리면 안되는데 느려지는 문제가 발생한 거고" | 이 한 문장이 결정 기록의 제목, 범위, 끝나는 조건을 바꿈 |
| 직감의 근거 묻기 | "아무리 봐도 요청 1개에 여러 로직이 섞이는건 안될거 같은데 왜이런 생각이 드는거지?" | 장애 격리, 단일 책임, 일관성 경계로 이름 붙임 → 2단계 설계 방향 |

### 4.4 AI의 과설계를 깎았다

AI는 일반론(보안, 확장성, 완결성)으로 설계를 키우는 경향이 있었다. 사용자는 프로젝트 맥락으로 그것을 줄였다.

- 새 로그인 경로 → 기존 개발용 로그인 + 이메일 패턴("어차피 사이드 프로젝트라서")
- 인공 요청만 골라 거르는 샘플링 → 불필요("인공 사용자가 99.9% 일거임")
- 발생기용 Prometheus 지표 → 보류("lightsail의 console에서 metric을 보거나 cli로 보면 될거 같은데")
- DataSource 래퍼 → 코드 0줄(3.3)
- 커스텀 경보 컨테이너 → Grafana 내장 경보(3.7)
- 55분 뒤 재확인 예약 → 취소("열어서 확인했어. 그러면 왜 55분 뒤에 한번더 확인하는거야?")

반대로 AI가 지나치게 조심할 때는 밀어붙였다. 실시간 경보를 "나중"으로 미루자 "실시간 경보도 지금 해줘", 팀원 코드 삭제를 거절하자 "방금 얘기 끝났어. 내가 다 해결한다고"로 사람 사이의 합의를 근거로 풀었다.

### 4.5 기록을 시스템으로 만들었다

- **결정 기록(`notes/decisions/`, 22건).** 사용자가 10-29에 "중간중간 결정 기록을 작성할 수 있도록 해줘. 방금 대답도 적어주면 좋을듯"이라고 하면서 시작됐다. 틀(`notes/README.md`)에는 "사용자가 정한 값과 가정으로 채운 값을 표시해 구분한다", "한번 쓴 결정은 고치지 않고, 바뀌면 새 기록을 쓴다"는 규칙이 있다.
- **판단 과정 기록.** "중요한건 내 판단과 결정의 과정이 문서로 기록되었으면 좋겠어. 대화에도 기록되지만 문서로 기록되는건 또 다른거잖아." 그래서 3.1의 결정 기록에는 누가 어떤 근거로 판단을 바꿨는지 12단계 표가 있다.
- **독자를 정해 자체 점검.** "6개월 뒤 프로젝트에 대해 아무 정보도 기억나지 않아도 빠르게 상황을 파악하고 통계를 읽고 이해할 수 있도록 작성했는지 확인하고 개선해줘", "제 3자 혹은 수개월 뒤의 나, 우리 팀원이 읽었을 때 행위가 납득가야해." 이 점검에서 Claude가 자기 문서의 틀린 주장 두 개와 순환 논리를 스스로 찾아냈다.
- **용어집.** Claude가 독자를 위해 내부 용어를 풀어 쓰자 사용자가 되돌렸다. "내부 용어는 소통의 원활함을 위해 필수적인 것도 있어. 내용을 풀어쓰기 보단 정리해두는게 더 좋아." 그 결과 `docs/glossary.md`가 생겼다.
- **페르소나 변경 기록(`docs/persona-changes/`).** "어느 날부터 데이터 모양이 달라졌나"와 "비교에서 뺄 날"을 찾기 위한 기록이다.
- **일회성 분석을 루틴으로.** 피크 통계를 매일 기록하는 스크립트(`collect.py`, 문서 5개)와 매주 관측 데이터 백업을 만들었다.

### 4.6 피드백을 영속 규칙으로 바꿨다

AI는 세션이 끝나면 잊는다. 사용자는 교정할 때마다 그것이 **다음 세션에도 적용되는 형태**로 남게 했다. 이 프로젝트에서 생긴 규칙과 그 계기다.

| 규칙 | 계기 | 저장 위치 |
|---|---|---|
| 작업 단위마다 커밋, 수정은 amend 대신 새 커밋 | "나는 작업 단위로 커밋하는걸 좋아해" (10-28) | 메모리 `commit-per-task` |
| 결정은 날짜별 파일로, `notes/`는 이 저장소에서 추적 | 전역 지침과 다른 저장소 전용 규칙 (10-29) | 메모리 `decision-log-in-notes` |
| 위임 문서는 루트에 untracked | "내가 직접 이동시키면서 작업시킬거임" (10-29) | 메모리 `delegation-docs-untracked` |
| 독립 작업은 서브에이전트로 병렬, 작은 일은 직접 | Claude가 혼자 순차 구현을 시작하자 중단시키고 "서브에이전트를 적절히 사용할 것." (10-29) | 메모리 `use-subagents` |
| 내부 용어는 그대로, 뜻은 용어집 한 곳에 | 과잉 풀어쓰기 교정 (11-03) | 메모리 `glossary-over-paraphrase` |
| 경보는 바로 움직여야 하는 것만 | 첫 경보 세트 반려 (11-09) | 메모리 `alerts-actionable-only` |
| 시퀀스 다이어그램은 메시지마다 화살표, `@Transactional`과 autocommit 구분, 약점을 드러낸 부하는 원인이 아니다 | 다이어그램 세 번 반려, 원인 판단 반박 (11-11) | 메모리 `diagram-and-analysis-feedback` |
| 다음 세션 시작 때 남은 일을 먼저 알려라 | "나중에 다시 클로드 코드 열어서 작업할 때 이거 하세요~ 라고 하면서 알려주셈" (11-09) | 메모리 `pending-followups` |
| 그림에 설정 주입은 설정이 동작을 바꿀 때만 | "이 스킬에 항상 뭔가 인프라 설정을 알려주던데" (11-12) | 스킬 `code-flow-diagram/SKILL.md` 자체를 수정 |
| 서브에이전트는 Orca CLI로 띄운다(사람이 터미널을 볼 수 있게) | (11-04, 서비스 저장소) | 서비스 저장소 메모리 |
| push·MR 전에 허락, 병합은 사람 | "mr을 올리기 전 나에게 허락을 맡아" (11-04, 서비스 저장소) | 서비스 저장소 메모리 |

그 위에 **이 프로젝트 이전부터 쌓아 둔 개인 하네스**가 있다.

- 전역 지침(`~/.claude/CLAUDE.md`): 서브에이전트 운용 규칙(git 금지, 파일 소유권, 범위 밖 보고, 기준선 숫자, 보고 재검증, 앞 작업의 함정을 다음 지시서에), 검증 규칙(skipped 수 확인, 조용히 꺼지는 검사 금지), 문서 규칙("확인 필요" 표시)
- 직접 만든 스킬: `write-mr`, `mr-body`, `code-flow-diagram`, `change-quiz`, `feature-brief`, `spec-summary`
- 직접 만든 출력 스타일 `fluent-korean`: AI 한국어의 조사 생략, 명사구 종결, 비유 남용을 막는 지침
- 상태 표시줄 스크립트(모델, 컨텍스트 사용률, 5시간 한도)

전역 지침의 서브에이전트 규칙은 대부분 이 프로젝트의 지시서에 그대로 나타난다. 즉 **규칙을 한 번 정하면 AI가 매번 그것을 적용**하는 구조였다.

### 4.7 권한을 단계적으로 넘기고, 바깥으로 나가는 행위는 붙잡았다

- 운영 서버 첫 확인 실행은 사용자가 직접 돌렸고, 그다음 병합·배포를 위임했고, 그 뒤 조건부 자동 변경(조건 네 개를 만족하면 배율을 올리는 예약)까지 미리 승인했다.
- 승인은 "ㅇㅇ", "ㄱㄱ"처럼 아주 짧지만, **머지와 배포는 매번 단어로 명시**했다("머지 때리셈", "배포 ㄱㄱ"). Claude는 "머지하라는 말이 없으면 머지하지 않는다"를 지켰다.
- 부작용 있는 작업 뒤에는 감사를 요구했다. "정확히 뭘한거지? 서버에 배포한 후 뭘한거야?" → Claude가 서버를 바꾼 작업과 읽기만 한 작업을 나눠 11단계로 보고했다.
- 발표를 앞두고는 "지금 locust 끄자. 이제 곧 발표라서 변수를 두면 안될듯"으로 운영 판단을 직접 내렸다.

### 4.8 비용 감각

- 검증 비용이 이득보다 크면 끊었다. "개오래 걸리는데 그냥 적당히 하고 그만하자. 아마 될거임."
- 작업 순서를 비용으로 정했다. "일단 이모지 ㄱㄱ. 금방 끝나잖아."
- 토큰 사용을 의식했다. "최소한의 토큰 사용을 위해 명령어로 옮겨주셈." → Claude가 파일을 읽고 쓰는 대신 `cp` 한 줄로 처리했다.
- 위임이 오히려 느리면 위임을 줄였다(다른 프로젝트 메모리: "걍 니 혼자 고치는게 맞지 않나? 시간도 너무 오래 걸리고 효율도 안나는데").

## 5. Claude의 작업 방식 (직접 지시하지 않았지만 일어난 것)

### 5.1 표준 작업 흐름

대화 기록에서 반복되는 흐름을 정리하면 다음과 같다.

```text
메모리·지침 읽기(server-access, commit-per-task 등)
 → 근거 시점 고정: 서비스 저장소는 git fetch 뒤 origin/main 기준으로 읽고 커밋 해시를 보고에 적음
 → 조사·측정 (SSH 읽기 전용, Prometheus·Tempo·Loki·Locust CSV, AWS CLI/MCP)
 → 결론 먼저 + 근거 표 + "확인 필요" + "정해 주셔야 할 것"
 → (승인) 구현: 독립 작업은 서브에이전트, 공유 파일(README, notes)은 직접
 → 재검증: 테스트를 직접 다시 돌리고 skipped까지 보고
 → 작업 단위 커밋 → 결정 기록·용어집 갱신 → 메모리 갱신
 → PR(write-mr 스킬) → 사용자 머지 → 배포 후 몇 분 확인
```

### 5.2 서브에이전트 운용

| 항목 | 값 |
|---|---|
| 이 저장소 세션의 서브에이전트 | 19개(10-29 12개, 10-30 3개, 11-09 2개, 11-11 독립 리뷰 2개) |
| 병렬 실행 | 10-29에만 네 쌍. 11-09에는 한쪽을 별도 worktree로 격리 |
| 서비스 저장소 | Codex를 Orca CLI로 띄워 구현, Claude 리뷰 세션 R1·R2를 따로 띄움 |

**지시서는 네 단계로 진화했다.**

1. **최소형(파일 이동).** 할 일 / 지킬 것 / 보고할 것. 이미 git 금지, 허용 경로, 범위 밖 보고, 검증 숫자("208줄인지")가 있었다.
2. **구조화(사용자 개입 직후).** 목표·배경(왜 하는지), "확정된 설계(바꾸지 마세요. 문제가 보이면 보고하세요)", 반드시 피할 함정, 테스트 기준선("24 passed, skipped 0"), 병렬 간섭 안내("당신이 고치지 않은 파일 때문에 실패가 보이면 고치지 말고 보고"), 서로 배타적인 허용 파일 목록, README는 문장 제안만.
3. **함정 전달.** 앞 에이전트의 범위 밖 보고를 다음 지시서의 함정으로 넣었다(예: "요약 API는 미래 날짜에 400" → 다음 지시서에 "계획 시각은 반드시 한국 시간대를 붙일 것").
4. **누적 함정 목록과 재량.** Windows 함정(venv `python.exe`가 자식 프로세스를 띄움, Locust 웹 UI는 IPv6, 콘솔 cp949, CSV 빈 줄), Locust 이벤트 인자, 에이전트별 계정 번호 범위와 compose 프로젝트 이름 분리, 실제 서버 접속 금지. 동시에 "권장 방향, 더 나은 방법이 있으면 근거와 함께 바꿔도 됩니다"로 재량을 주었다. 실제로 한 에이전트는 권장안을 재 보고(1.7초) 더 빠른 방법(0.9초)을 택했다.

중간에 지시서가 약해진 순간도 있었다. git 금지 목록을 줄여 쓴 지시서를 받은 에이전트가 읽기 전용 git 명령을 썼고, 그 뒤 지시서에 "읽기 전용 명령도 금지, 다른 에이전트가 같은 작업 트리에서 일하고 있다"는 이유까지 적었다.

**재검증.** 다른 에이전트가 작업 중일 때는 **커밋 상태만 임시 git worktree로 떼어** 전체 테스트를 돌렸다. 라이브러리 동작은 설치된 Locust 소스를 직접 읽어 확인했다. 다시 돌리지 못한 것은 "이 항목은 보고이고 제가 다시 돌려 보지는 않았습니다"로 구분했다.

**범위 밖 보고가 찾은 실제 결함 3건.**
- 실행기 부족 경고가 이벤트 인자 오류로 **한 번도 동작하지 않았다**(단위 테스트는 순수 함수만 봐서 통과).
- Worker 두 개가 함께 재시작하면 트래픽이 **영구히 멈췄다**.
- 계정 2만 개의 하루 일정 생성에 **12초**가 걸려 그동안 세션 실행이 막혔다(0.9초로 개선).

### 5.3 검증 기법

| 기법 | 사례 |
|---|---|
| skipped까지 보고 | 모든 보고에 "N passed, skipped 0". 테스트 23 → 366건 동안 건너뜀 0 유지 |
| 바뀌지 않아야 할 것의 증명 | 리팩터링 전후 일정의 sha256 지문 대조, 이전 코드를 `git archive`로 꺼내 일정 7,957건 대조 |

| 반영 뒤 상태 비교 | Grafana `apply` 뒤 `diff` 종료 코드 0, 관측 서버 파일 교체 뒤 md5 비교 |
| 조용히 꺼지지 않는 설계 | 웹훅이 비면 compose 전체가 멈춤, Prometheus 접속 실패 시 보고서 중단, 매일 9시 메시지가 없으면 감시가 죽은 것 |

### 5.4 안전 경계

- 공유 서버에 쓰기 전에는 매번 확인을 받았고, 바꿀 파일만 타임스탬프 백업을 떴다(`.env`, 상태 DB, 관측 설정).
- 자동 모드 권한 분류기가 여러 번 거부했다(지시 없는 PR 머지, 실서버 실행, 모든 ssh 종료, 외부 CDN 스크립트 실행, 운영 서버 읽기). Claude는 **우회하지 않고** 범위를 좁히거나(해당 PID만 종료), 다른 방법을 쓰거나(그림을 PIL로 렌더링), 사용자가 직접 실행하게 넘겼다(`!` 명령).
- 비밀값은 `grep -iv "secret|token|pass|key"`로 거르고 웹훅은 `sed`로 가려 보여 줬다. 채팅에 웹훅이 붙여 넣어지자 재발급을 권했다.

## 6. 의식하지 못했을 수 있는 패턴

### 사용자 쪽

1. **승인은 아주 짧고 질문은 길다.** "ㅇㅇ", "pr ㄱㄱ"와 여러 문장짜리 의심이 대비된다. 장점은 속도지만, AI가 승인 범위를 넓게 해석할 위험이 있다(예: "공통 세션부터"를 좁게 해석해 페르소나 추가를 빠뜨림).
2. **"근데"로 시작하는 질문이 방향 전환의 신호다.** "근데 2번은...", "근데 grafana 코드는...", "근데 중요한 정보만..."은 거의 모두 설계 변경으로 이어졌다.
3. **위임한 뒤 꼭 "어떻게 했냐"를 묻는다.** 경보 하나에만 구현 방식을 묻는 질문이 네 번 나왔다. 결과를 받아들이기 전에 머릿속 모델과 맞춰 본다. 그래서 AI의 용어 혼동과 사용자의 오해가 둘 다 드러났다.
4. **"현실성"으로 해상도를 올린다.** 사진 없음 → 운동 없음 → 다이어터도 운동 → 사람마다 다른 무게 → 사람마다 다른 종목 → 종목을 못 찾는 소수. 매번 "실제 사용자라면"을 기준으로 한 단계씩 올렸다.
5. **이해가 막히면 그림을 요구하고 형식을 지정한다.** 시퀀스 다이어그램, DB를 오른쪽 열에, 화살표 하나씩, 실측 시간 표기. 그림이 설명이 아니라 **분석 도구**로 쓰였다.
6. **대안을 나란히 만들게 해서 고른다.** Excalidraw와 Mermaid를 둘 다 만들게 한 뒤 하나를 지웠다.
7. **위험 허용 수준을 스스로 말한다.** "사이드 프로젝트라서", "인공 사용자가 99.9%". AI가 일반론으로 키운 설계를 이 한마디로 줄였다.
8. **"내 눈으로" 확인하려 한다.** 로컬 스택 띄우기, Grafana Explore 절차 요청, 대시보드 직접 만들기. 화면에서 재현할 수 있어야 받아들인다.
9. **결정은 사람과 합의한 뒤에 가져온다.** Growth 담당자, 인프라 담당 팀원과의 합의는 대화 밖에서 하고 결과만 지시했다.
10. **가끔 과하게 단정한다.** "A는 rest 계약을 애초에 지키지 않으니까"처럼 단정했을 때 Claude가 정정했고, 사용자는 그 반박을 받아들였다.

### Claude 쪽

1. **가까운 원인부터 고치자고 권하는 경향.** 발생기 0초 몰림 수정, 조회에서 지급 제거, 래퍼 개선. 사용자가 근본 원인 쪽으로 끌어당긴 뒤에야 바뀌었다.
2. **그림을 처음엔 압축한다.** 카드에 텍스트를 몰아넣고 설정 구역을 기본으로 넣었다. 지금은 메모리와 스킬로 고정되었다.
3. **응답이 "정해 주셔야 할 것"으로 끝난다.** 기록 누락은 적지만 사용자가 매번 결정해야 한다.
4. **자기 오류를 먼저 밝힌다.** "앞선 제 설명이 틀렸습니다", "실수가 하나 있었습니다"(테스트가 돌지 않은 상태에서 PR이 병합된 일을 스스로 보고).
5. **세션 사이 지식이 이어지지 않는다.** 11-05 한 세션이 이미 밝힌 원인을 같은 날 다른 세션이 "확인 필요"로 남겼다. 11-05에 찾은 0초 몰림이 11-11에 다시 발견되었다. 메모리에 남기지 않은 분석은 다음 세션에서 미지수가 된다.
6. **워크트리 기준으로 생각하다 main의 변경을 놓친다.** 다른 팀원의 병합(PR 뱃지 제거, 누적 뱃지 추가)을 두 번 늦게 발견했다.
7. **긴 도구 작업 뒤 영어로 말하는 습관.** 여러 프로젝트에서 "한국어로 해줘" 교정이 반복됐다.

## 7. AI의 실수와 교정

AI의 실수는 숨길 일이 아니라 **운용 능력을 보여 주는 증거**다. 누가 어떻게 잡았는지가 중요하다.

| 실수 | 누가 잡았나 | 교정과 이후 |
|---|---|---|
| "전용 도메인이 없으면 구분 불가" → 새 로그인 경로 권장 | 사용자의 되묻기 | 기존 로그인 + 이메일 패턴, backend 코드 변경 없음 |
| Locust 재분배 동작을 틀리게 설명(README에도 기재) | 사용자의 실험 요구 | 실측으로 정정, 옵션 강제 |
| 혼자 순차 구현 시작 | 사용자 중단 | 서브에이전트 병렬, 메모리 규칙 |
| TPS 기준을 밝히지 않고 세션 수로 보고 | 사용자의 연속 질문 | 용어 세 개 정의 |
| 기존 계정을 나눠 새 페르소나를 만드는 설계 | 사용자("완전 새로운 계정아니야?") | 페르소나마다 1만 칸 번호 구간 예약 |
| 사용자 제안을 "70/30"으로 잘못 정리 | 사용자 반려 | 90% 무리·60% 무리 절반씩 |
| 0초 몰림을 발생기 탓으로 분류, 발생기 수정 권장 | 사용자("당연한거야?") | 서버 결함으로 재정의, 메모리 규칙 |
| 다이어그램에 "트랜잭션 없음" 표기 | 사용자 | `@Transactional`과 autocommit 구분 |
| DataSource 래퍼를 개선하자는 제안 | 사용자("어려운 구현으로 가는것이 아닌가?") | 코드 0줄 |
| 테스트가 돌지 않은 상태에서 PR #8 병합(파이프 뒤 `tail`의 종료 코드로 다음 명령이 실행됨) | Claude 자진 보고 | 병합 직후 296건 통과 확인 |
| 이미 병합된 PR 브랜치에 push | Claude 발견 / 사용자 발견(각 1회) | 새 브랜치로 체리픽·rebase |
| 공용 `git stash` 실행 | Claude 자진 보고 | 자기 항목만 SHA로 적용 뒤 삭제 |
| 고아 span 원인을 "15초 health check"로 설명 | 사용자의 네 갈래 질문 → Claude가 배포 시각 대조로 정정 | 배포 스크립트가 원인 |
| 덧셈 실수(DB 문장 39개 → 실제 37개) | Claude가 사용자 질문에 답하다 발견 | 문서와 그림 모두 수정 |

**교훈.** AI의 판단이 틀린 장면 대부분은 사용자의 **"왜?", "당연한가?", "코드가 그래?"** 질문에서 드러났다. 반대로 Claude가 스스로 잡은 실수는 주로 **숫자와 실행 결과**(테스트, 재계산, 대조)에서 나왔다. 사람은 전제와 방향을, AI는 계산과 일관성을 검증하는 분업이 자연스럽게 생겼다.

## 9. 쓸 때 주의할 점

- **`GET /growth/me`의 개선 수치는 아직 없다.** 수정은 병합되었지만 운영 효과 측정(Tempo와 하루 요약으로 "효과 측정" 표 채우기)은 남아 있다. "원인을 정량화하고 수정을 병합했다"까지가 사실이다.
- **16,000·20,000명 단계는 진행하지 않았다.** 20,000명은 서비스가 가정한 규모이고 계획만 있다.
- **k6 한계 측정은 보류되었다.** "처리량 한계를 측정했다"고 쓰지 않는다.
- **2단계(조회 요청에서 쓰기 분리)는 설계 논의까지만** 했다(비동기 + 아웃박스 + 재시도 방향).
- **데이터 품질 개선의 실제 달성률은 확인하지 않았다.** 예상치(67~72%)만 있다.
- 서비스 저장소의 운영 문서와 ADR은 "제안" 상태였다. "제안·작성했다"로 쓰는 편이 정확하다(확인 필요).
- 경보 일부는 팀원의 기존 작업과 통합한 결과다. 단독 작업처럼 쓰지 않는다.
- 인계 문서 `locust-traffic-generator-handoff.md`를 쓴 설계 에이전트의 세션은 찾지 못했다(확인 필요). 근거가 된 설계 세션은 서비스 저장소의 10-28 Claude 세션이다.
- 하루 요약 도구는 Master를 재시작한 날 요청을 적게 센다(11-09: 109,550건 vs 실제 158,196건). 미결로 남아 있다.
