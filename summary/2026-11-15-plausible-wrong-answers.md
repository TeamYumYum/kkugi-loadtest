"그럴듯한 오답"은 **근거를 갖춘 말투로 제시했지만 틀렸거나, 확인하지 않은 전제 위에 서 있던 답**을 말한다. 질문을 잘못 읽은 경우(동문서답)와 Claude가 맞았던 경우는 따로 나눴다.

## 1. 그럴듯한 오답 (17건)

### 1.1 "개발용 로그인으로는 인공 회원을 구분할 수 없다" (10-28 ~ 10-29)

- **Claude의 답(10-28 18:02).** 운영에 쓸 인공 계정 로그인으로, 비밀값 헤더로 보호하는 새 경로 `POST /auth/login/synthetic`과 새 provider `SYNTHETIC`을 만들자고 인계 문서까지 썼다. 근거는 "IP 제한은 쓸 수 없고, **전용 도메인도 없습니다. 그래서 새 provider가 인공 계정을 구분하는 기준이 됩니다**"였다.
- **사용자(10-29 09:04).** "개발용 로그인으로는 왜 안된다고 했지? 단순히 서버에 켜지 않아서가 아니잖아"
- **Claude의 두 번째 답.** 바로 인정하지 않고 근거를 더 정리해 다시 방어했다. "앞에서 확인했듯이 전용 도메인이 없어서 이메일로도 둘을 나눌 수 없습니다."
- **이상하다고 느낀 지점.** 서버에 꺼 둔 것은 지금 상태일 뿐 이유가 아니라는 점, 그리고 "도메인을 소유해야 구분된다"는 전제였다.
- **확인한 방법.** 위험 허용 수준을 직접 정하고 더 단순한 대안을 내놓았다. "어차피 사이드 프로젝트라서 이메일만으로 인증이 끝나도 상관없긴함. 그냥 개발자용 로그인한 사용자인 경우 이메일이 기록에 같이 남으면 안되나?" 그러자 Claude가 코드를 확인하고 "제가 앞에서 '전용 도메인이 없으니 구분할 수 없다'고 판단한 것이 틀렸습니다"라고 인정했다. 개발용 로그인은 이메일을 검증하지 않으므로 예약 도메인 패턴(`lt-%@synthetic.kkugi.test`)으로 충분했다.
- **한 번 더 검증.** "그렇게 되면 로그나 추적에 그렇게 기록이 남는거야? ... **코드가 그렇게 되어 있어?**" Claude가 코드를 확인하니 이메일 구분은 DB까지만 되고 지표·로그·추적에는 남지 않았다. 그래서 지표에 값 두 개짜리 `synthetic` 태그를 더하는 작업이 생겼다.
- **결과.** backend 코드 변경 없이 해결. 처음 인계 문서는 버리고 새로 썼다.

### 1.2 "새로 붙은 Worker에는 실행기를 다시 나누지 않는다" (10-29)

- **Claude의 답(10-29 오전).** "Locust는 기본적으로 **이미 나눠 준 User를 다시 나누지 않습니다.** 노트북은 User를 0개 받습니다." 같은 문장이 README에도 들어가 있었다.
- **사용자(11:32).** "그럼 테스트를 해보자. rebalance-enableing도 테스트 해보고 서버 부하도 테스트 해보자."
- **이상하다고 느낀 지점.** 직접 반박하지는 않았다. 노트북 Worker를 붙였다 뗄 운영이 이 동작에 달려 있었으므로 말 대신 실험을 요구했다.
- **확인한 방법.** 로컬에서 Master와 Worker 둘을 붙였다 떼는 실험.
- **결과.** "'다시 나누지 않는다'는 제 설명은 **확인하지 않고 한 말이었고, 틀렸습니다.**" 실제로는 붙을 때는 다시 나누고, **떨어질 때 실행기가 사라진 채 남는 것**이 진짜 문제였다. README를 고치고(`7d0004e`), `--enable-rebalancing` 없이는 Master가 시작하지 않게 했다.

### 1.3 "계정 2만 개도 서버 Worker로 충분하다" (10-29)

- **Claude의 답(17:5x).** "2만 개에 필요한 실행기는 약 56개라 서버 Worker로 충분합니다."
- **사용자(17:56).** "아 뭐야. 2만개를 4gb서버에서 실행시켜도 문제가 전혀 안된다는거야? cpu랑 네트워크 모두? **저번에는 모니터링 대시보드에 문제가 생길수도 있다고 했는데**"
- **이상하다고 느낀 지점.** 앞서 들은 위험 설명과 지금의 단정이 서로 맞지 않았다.
- **결과.** "제가 '서버 Worker로 충분하다'고 한 것은 **실행기 수만 계산한 이야기**였습니다. ... 그렇게 들리게 말한 것은 제 잘못입니다. **아직 측정하지 않았습니다.**" 이후 단계마다 CPU 크레딧과 관측 데이터 증가량을 재는 항목이 다시 확인됐다.

### 1.4 "페르소나를 더하면 기존 계정이 깨진다" (10-30)

- **Claude의 답(16:58).** 페르소나를 더하지 않고 멈춘 이유를 설명했다. "페르소나를 하나 더하는 순간 지금 돌고 있는 계정들이 깨지기 때문입니다." 그리고 해시 구간 고정과 generation을 올려 재가입시키는 해결안을 냈다.
- **사용자(16:59).** "뭔소리야? 왜 기존 계정이 깨지는거지? 완전 새로운 계정아니야? 혹시 1000명 내에서 페르소나를 나누려고 하는건가?"
- **이상하다고 느낀 지점.** 설명 전체가 "기존 1,000개 계정을 나눠 쓴다"는, 말하지 않은 전제 위에 서 있었다. 사용자의 의도는 트래픽을 늘리는 것이었다.
- **결과.** "네, 맞습니다. 설계안은 지금 있는 계정 1,000개를 비중대로 나눠 쓰는 방식이었습니다." 새 페르소나는 새 번호대 계정으로 바뀌었고, 구현이 더 단순해졌다. 이후 "페르소나마다 1만 칸 번호 구간"이라는 규칙의 출발점이 됐다.

### 1.5 TPS가 RPS보다 작다, "요청 하나에 트랜잭션이 여러 개 들어가는 구조는 아니다" (11-02)

- **Claude의 첫 답(14:28).** 표에 "TPS (완료 세션) 0.047"을 RPS 0.28 옆에 적었다. 기준은 README의 "업무 처리량"이었지만 표 제목만으로는 드러나지 않았다.
- **사용자(14:29).** "왤케 얼마 안되지? 그리고 rps보다 tps보다 낮은 이유가 뭐야? **request 1개에 transaction이 여러개 들어가는거 아냐?**"
- **Claude의 두 번째 답.** 세션으로 셌다고 밝힌 뒤 DB 지표를 조회해 "요청 하나에 DB 커밋은 평균 1개 정도입니다. ... **요청 하나에 트랜잭션이 여러 개 들어가는 구조는 아닙니다**"라고 답했다. 그리고 "앞으로 TPS는 이 DB 커밋 기준으로 보고하겠습니다"라고 사용자 쪽 정의로 바로 옮겨 갔다.
- **사용자(14:36, 14:44).** "tps를 원래 그렇게 정의하는거야? db 트랜잭션을 기준으로 정의하는거 아님?" → "**너는 아까 어떤 기준으로 산정했는데?**"
- **이상하다고 느낀 지점.** 숫자의 정의가 답할 때마다 흔들렸다. 그래서 일반론 대신 Claude가 실제로 쓴 계산 방법을 밝히게 했다.
- **결과.** Claude가 원자료(Locust CSV의 `SESSION` 줄), 넣은 것과 뺀 것, 계산식을 공개했다. 용어를 TPS(=RPS, HTTP 요청), 세션/s, DB TPS 셋으로 나눠 README와 용어집에 정했다. "요청당 커밋 0.9"도 나중에 이상 구간을 빼면 0.75라고 스스로 고쳤다.
- **9일 뒤 드러난 것.** "요청 하나에 트랜잭션이 여러 개 들어가는 구조는 아니다"는 평균으로는 맞았지만 구조에 대한 결론으로는 틀렸다. 11-11 분석에서 `GET /growth/me` 한 요청이 **DB 트랜잭션 7개**(`@Transactional` 5개, autocommit 2개)를 연다는 것이 밝혀졌다. 11-02의 사용자 직감이 이 API에서는 맞았던 셈이다. 단서는 그때 이미 있었다. Claude는 같은 답에 "커넥션을 빌린 횟수(2.6회)가 커밋 수(0.9회)보다 많습니다. ... 확인 필요"라고 적어 두었지만 더 파지 않았다.

### 1.6 "Locust와 대시보드가 다른 이유는 Spring 바깥의 대기 시간" (11-04, 서비스 저장소)

- **Claude의 답(11:0x).** Locust p95가 1초를 넘는 이유로 TLS, nginx, Tomcat 스레드 대기처럼 backend 지표에 잡히지 않는 시간을 들었다. "이 시간이 차이의 원인으로 의심됩니다."
- **사용자(11:12).** "그게 뭔소리야? locust랑 대시보드랑 왜 다른데? locust가 요청을 보내고 받는 동안에 시간을 측정했으니 이게 정확한건가? 네트워크까지 걸쳐지는 시간까지 계산된건가?"
- **사용자의 가설(11:18).** "지금 locust에 보이는 1000ms이상의 숫자는 그러면 **맨 처음 가사 사용자를 늘릴 때 한번에 실행한 기록이 보이는거지?**" ("가사"는 원문 그대로의 오타로, 가상 사용자를 뜻한다)
- **확인한 방법.** Claude가 "아직 확정하지 못했다"고 답한 뒤 Locust의 1분 단위 누적 기록(`stats_history.csv`)으로 구간을 나눴다.
- **결과.** 1초 넘는 값은 모두 시작 직후 1분(실행기 422개가 한꺼번에 로그인)에 생겼고, Locust 표는 누적값이라 그 1분이 계속 남아 있었다. 그 뒤 5,566건의 1분 평균 최악값은 260ms였다. 처음 의심한 "Spring 바깥 대기"가 아니라 **사용자의 가설이 맞았다.**

### 1.7 "고아 span은 15초마다 오는 health check 때문" (11-05, 서비스 저장소)

- **Claude의 답(11:2x).** "health check는 DB 상태를 확인하려고 커넥션을 빌립니다. 그래서 부모 없는 `getConnection` span과 `Ping` span이 Tempo에 남습니다. ... health check 때마다 쓸모없는 trace가 계속 쌓입니다."
- **사용자(11:27).** "고아 span이 왜 남는지, 뭐 때문에 남는지, 무슨 변경사항으로 인해 남는지, 그걸 왜 감수해야하는지 모르겠어."
- **이상하다고 느낀 지점.** 설명을 네 갈래로 쪼개 물었다. 특히 "무슨 변경사항으로 인해"는 원인의 시점을 묻는 질문이었다.
- **확인한 방법.** Claude가 고아 span이 생긴 시각을 10분 단위로 세어 배포 시각과 대조했다.
- **결과.** "앞에서 제가 한 설명 하나가 틀렸습니다." 고아 span은 15초마다가 아니라 배포 시각(10:51, 11:12, 11:19)에만 몰려 있었다. 원인은 배포 스크립트가 반복 호출하는 health 확인이었다.

### 1.8 "`ssh kkugi-obs-grafana`로 터널을 여세요" (11-05, 서비스 저장소)

- **Claude의 답(14:5x).** Grafana Explore 사용법을 안내하며 "터미널에서 `ssh kkugi-obs-grafana`를 실행해 터널을 엽니다. 이 alias는 PC의 13000 포트를 관측 서버 Grafana의 3000 포트로 연결합니다."
- **사용자(16:05).** "localhost:13000가니까 안뜨는데. 권한 허용할테니 여기서 해봐."
- **확인한 방법.** 안내대로 직접 해 보고 안 되자 Claude에게 권한을 넘겨 직접 확인하게 했다.
- **결과.** 그런 alias는 없었다. 실제 alias(`kkugi-obs-tunnel`)로 바로잡고, 틀린 내용이 들어 있던 메모리에 "`kkugi-obs-grafana`라는 alias는 없다"를 적었다. 메모리에서 읽은 내용을 확인 없이 안내한 사례다.

### 1.9 "Grafana 경보는 문서로 재현 가능하다" (11-10)

- **Claude의 답(10:3x).** 작업 내역 체크리스트에 대해 "문서로 재현 가능한가. 경보 8개의 조건이 `alerting.yaml`에 그대로 있습니다 ..."
- **사용자(10:34, 10:39).** "니가 무슨 작업한거야? - 이모지 해결했고, - 재은이 코드 지웠고, ... - GRAFANA도 재실행할 필요 없고, 이거 맞지?" → "**아니 그래서 재현 가능하다는거지?**"
- **이상하다고 느낀 지점.** 긴 설명이 예/아니요를 흐렸다. 끝난 상태를 체크리스트로 대조하게 했다.
- **결과.** Claude가 단서를 드러냈다. 이모지 수정 등 두 항목은 "코드만 완료, 아직 반영 안 됨"이었고, 재현은 "가짜 Grafana 테스트로만 확인했습니다. 실제 Grafana에서는 아직 읽기만 해 봤습니다." 머지 뒤 실제 서버에서 `apply`와 `diff`(종료 코드 0)로 확인했다. 질문이 "재현 가능"이라는 주장을 실측 검증으로 바꿨다.

### 1.10 "결함의 상당 부분은 우리 발생기가 만든 것" (11-11)

- **Claude의 답(12:3x).** "결론부터 말씀드리면, **결함의 상당 부분은 우리 발생기가 만든 것이고**, 그 몰림이 backend의 약점을 드러냈습니다." 발생기의 매분 0초 몰림을 먼저 고치자고 권했다.
- **사용자(12:37).** "**1초내에 같은 api가 40-50건이 들어오면 느려지는게 당연한거야?** 그게 아니라면 발생기의 문제가 아니라 서버의 문제라고 생각하는데."
- **이상하다고 느낀 지점.** 1초에 50건은 합격선(초당 60건)보다 작다. 그 정도에 느려진다면 원인은 부하가 아니라 서버다.
- **결과.** "아니요, 당연하지 않습니다. ... 제가 앞에서 원인을 나눈 방식이 틀렸습니다." "발생기를 먼저 고치자는 제 권장도 철회합니다. 지금 고치면 서버는 그대로인데 지연만 줄어 보여서, 문제를 가리는 결과가 됩니다." 대기열 계산(50 ÷ 10 × 95ms ≈ 475ms)이 관측 최대값과 맞는 것으로 서버 원인을 세웠다. 메모리에 "약점을 드러낸 부하는 원인이 아니라 조건"으로 남았다.
- **같은 오답이 6일 전에도 있었다.** 11-05 서비스 저장소 세션에서 Claude는 느린 1% 요청 229건 중 228건이 매분 0~3초에 시작한 것을 찾고도 "인공 트래픽 생성기가 만든 패턴일 가능성이 큽니다. ... **서버를 고칠 대상이 아닙니다**"라고 분류했다. 그때는 아무도 이 결론을 반박하지 않았고, 원인 확정이 6일 늦어졌다.

### 1.11 시퀀스 다이어그램의 "트랜잭션 없음" (11-11)

- **Claude의 답(14:4x).** `@Transactional`이 없는 호출을 그림에 "① 트랜잭션 없음"으로 표기했다.
- **사용자(14:49).** "이게 뭔 그림이지.? 내용이 너무 압축된거 같은데..? ... 그리고 트랜잭션이라고 부르는게 내 기준에서는 좀 헷갈리는게 code 에서 @Transactional 이 없는거고, **실제 쿼리를 동작할 때는 트랜잭션이 자동으로 시작되는거 아냐?**"
- **결과.** MySQL autocommit에서는 문장 하나가 곧 DB 트랜잭션이므로 표기가 틀렸다. "@Transactional 없음 (autocommit)"으로 고치고 결정 기록 문구도 바꿨다(`6f0df8c`). 화살표를 하나씩 펼친 그림에서 "DB 왕복 37번 중 26번이 트랜잭션 관리 문장"이 드러났다.

### 1.12 "조회에서 뱃지 지급을 빼자(B안)" (11-11)

- **Claude의 답(15:56).** "저는 **B(조회에서 뱃지 지급을 빼기)** 를 권합니다. ... 첫 기록 뱃지는 11-10부터 이미 기록을 저장할 때 지급되고 있어서, **남은 작업이 PR 뱃지를 옮기는 것 정도**입니다."
- **사용자(16:04).** "조회에서 뱃지 지급을 빼면 어떻게 뱃지 지급할거야? 지금은 뭔가 **의도가 growth/me를 호출하는 화면마다 뱃지 여부를 확인하려고** 그러는거 같은데."
- **이상하다고 느낀 지점.** 코드가 왜 그렇게 되어 있는지(설계 의도)를 확인하지 않고 내린 권장이었다.
- **결과.** Claude가 설계 문서와 커밋을 확인했다. "확인해 보니 말씀하신 의도가 맞습니다." 조회 시점 지급은 "저장 때 놓친 건을 받아 주는 안전망이자 PR 뱃지의 유일한 지급 경로"였다. B는 정책 변경이라 범위를 넘으므로 A(트랜잭션 묶기)로 바뀌었다.

### 1.13 `GrowthSummaryReader`가 Service를 부르는 구조 (11-11)

- **Claude의 코드.** 트랜잭션을 묶으려고 `GrowthSummaryReader` 클래스를 만들었고, 독립 리뷰 두 세션도 이 구조를 지적하지 않은 채 MR이 올라갔다.
- **사용자(17:23).** "아니 reader에서 service계층을 호출하면 어떡함"
- **결과.** 이 저장소에서 Reader는 서비스가 부르는 하위 부품인데 방향이 거꾸로였다. Reader를 지우고 `TransactionTemplate`으로 바꿨다(`b5e47b24`). Claude는 "두 리뷰가 이 구조를 보지 못했다"고 밝히고 재리뷰 여부를 사용자에게 넘겼다.

### 1.14 "GET은 첫 기록 뱃지만 지급한다" (11-12)

- **Claude의 답.** 2단계(조회 요청에서 쓰기 분리) 논의에서 GET이 지급하는 뱃지를 첫 기록 뱃지로만 설명했다.
- **사용자(10:52).** "뭔소린지 이해가 잘 안되네. 현재 growth me에 대한 로직 이해가 **너랑 내가 다른 것 같아.** /code-flow-diagram 를 통해 그림을 그려줘."
- **확인한 방법.** 말로 맞추는 대신 그림으로 같은 모델을 보게 했다.
- **결과.** Claude가 main 기준으로 그림을 그리다 스스로 발견했다. "앞에서 'GET은 첫 기록 뱃지만 지급한다'고 했는데, 이는 **638 워크트리를 기준으로 한 설명**이었습니다. 638이 병합된 뒤 633(누적 볼륨·단백질 뱃지)이 main에 병합되었고, 이 뱃지들은 GET에서만 지급됩니다." 자기 작업 공간을 기준으로 생각하다 팀의 최신 변경을 놓친 사례다(전날 635에서도 한 번 있었다).

### 1.15 "표준은 부수적인 쓰기까지 금지하지 않는다" (11-12)

- **Claude의 답.** GET이 상태를 바꾸는 것이 REST 위반인지에 대해, RFC 9110을 인용하며 "같은 절은 접근 로그나 조회수처럼 서버가 부수적으로 남기는 쓰기는 허용한다"는 예외를 먼저 꺼낸 뒤 "지금의 지급은 부수적인 쓰기가 아닙니다"라고 이었다.
- **사용자(11:09).** Claude의 문장을 그대로 인용하며 반박했다. "너가 ... 이렇게 말했는데 ... get에서 쓰기 작업을 하는게 아니다. 뭔가 간접적인 것이다. 이라는 **뉘앙스가 느껴져서** ... 다시 그림을 보니 내 말이 맞는거잖아. get에서 쓰기를 한다. 트랜잭션이 두개일 뿐이다."
- **결과.** "'지금의 지급은 부수적인 쓰기가 아닙니다'라는 문장은 원래 사용자의 말에 동의하려고 쓴 것이었습니다. 그런데 그 앞에 ... 예외를 먼저 꺼냈습니다." 해당하지 않는 예외를 꺼내 결론을 흐린 것을 인정했다. 사실관계는 틀리지 않았지만 **전달이 오답처럼 읽힌** 사례다.

### 1.16 "① 저장 시점 동기 지급 + 배치 보충" (11-12)

- **Claude의 답.** 2단계 해결책 ①로 "저장 시점 동기 지급만 남기고, 놓친 건은 주기 배치로 보충"을 제시했다.
- **사용자(11:18).** "너가 아까 말한 ①은 본래의 문제를 해결할 수 없는 쓰레기 방법 맞지?"
- **결과.** Claude는 단정에는 동의하지 않았다("쓰레기 방법은 아닙니다"). 대신 결함을 인정했다. "제가 처음 적은 형태는 633 이전의 코드를 전제로 해서 **누적 뱃지가 빠져 있었습니다.**" 1.14와 같은 원인(낡은 기준점)에서 나온 오답이고, 사용자의 과한 단정은 Claude가 바로잡은 양방향 교정 사례다.

### 1.17 추천 표시로 사용자 제안을 바꿔 놓은 질문 (11-09)

- **Claude의 질문.** 사용자는 "다이어터 중에서도 70%비율로 성공하는 사람과 실패하는 사람(30%)을 만들어줘. **아님** 다이어터 중에서도 50%는 매일 90%이상 목표 칼로리를 지키고, 나머지 50%는 60% 비율로 지키는 규칙을 세우던가"라고 두 안을 냈다. Claude는 선택지를 만들며 첫 안에 "성공 70% / 실패 30% **(추천)**"을 붙이고 "실패하는 사람은 거의 매일 목표의 60~80%를 먹거나 120% 넘게 먹습니다"로 풀었다.
- **사용자(선택지 답란에 직접 입력).** "근데 이렇게 정하면 **30%의 사용자는 계속 실패하는 걸로 뜨잖아.** 내 말은 90%이상 확률로 성공하는 무리 절반, 60%이상 확률로 성공하는 무리 절반으로 다이어터 그룹을 나누자는거였어."
- **결과.** 사용자 설명대로 구현했다. 선택지에 붙은 "추천"이 사용자 제안을 Claude의 해석으로 바꿔 놓을 수 있다는 것을 보여 준 사례다.

## 3. 되물었지만 Claude가 맞았던 경우 (대조군)

- **10-30 17:36 "종목을 직접 만드는 api가 서버에 없다는 말이야?"** Claude가 OpenAPI, 컨트롤러, DB 스키마, 원격 브랜치, 요구사항 문서 다섯 곳을 다시 확인했고 결론은 그대로였다(MVP1에서 일부러 뺀 기능).

되묻기가 언제나 오답을 찾은 것은 아니다. 되묻는 비용이 작고, 맞았을 때도 근거가 넓어진다(종목 API 사례는 다섯 곳 확인으로 PR에 남았다).

| 처음 지적받으면 근거를 보강해 방어함 | 1.1(첫 되묻기에 같은 주장 반복) | 없음 |
| 사용자 쪽으로 쉽게 쏠림 | 1.5("앞으로 DB 커밋 기준으로" → 다음 답에서 다시 바꿈) | 없음 |
| 선택지를 만들며 해석을 섞음 | 1.17("추천" 표시) | 없음 |
| 이름을 지어 붙임 | 2절(채널 이름) | 메모리 `glossary-over-paraphrase`는 반대 방향(내부 용어를 풀지 말 것)만 다룬다 |

### 짚어 둘 것

- **첫 번째 되묻기에는 오답이 버텼다.** 1.1에서 Claude는 첫 질문에 근거를 더 정리해 같은 주장을 반복했다. 사용자가 구체적 대안을 내놓은 두 번째에야 인정했다. 1.5에서도 정의가 두 번 흔들린 뒤 세 번째 질문("너는 아까 어떤 기준으로")에서야 계산 방법이 공개됐다. **한 번 되묻고 수긍하지 않은 것**이 여러 사례에서 결정적이었다.
- **사용자가 반박하지 않은 오답은 그대로 남았다.** 1.10의 "발생기 탓" 분류는 11-05에 이미 한 번 나왔지만 그때는 아무도 반박하지 않아 원인 확정이 6일 늦어졌다. 1.5의 "트랜잭션 여러 개 구조는 아니다"도 9일 동안 고쳐지지 않았다.
- **Claude가 스스로 찾은 오류도 많다.** 숫자와 실행 결과에서 나온 것이 대부분이다(덧셈 실수 39 → 37, 커밋 0.9 → 0.75, 테스트가 돌지 않은 상태의 병합 자진 보고, 11-11 "설득력" 점검에서 찾은 틀린 주장 두 개). 반면 **전제와 방향의 오류는 거의 모두 사용자가 찾았다.**

## 6. 포트폴리오에 쓸 때

- 대표 장면으로는 1.10(첫 원리 질문으로 원인 판단을 뒤집음), 1.1(위험 허용 수준을 정해 과설계를 깎고 코드로 확인시킴), 1.5(계산 근거를 요구해 용어 체계를 세움)를 권한다. 셋 다 결과물(서버 수정 병합, backend 무변경 해결, 용어집)로 이어졌다.
- "AI의 답을 믿지 않았다"보다 **"어떤 질문으로, 무엇을 근거로 확인했는가"** 를 쓰는 편이 설득력이 있다. 4절의 표가 그 재료다.
- 1.15, 1.16, 3절처럼 사용자의 단정을 Claude가 바로잡은 사례도 함께 두면, 일방적인 교정이 아니라 **서로 검증하는 구조**였다는 점이 드러난다.
